## 开场白

## 一、整体架构：四层加密体系

这是我设计的核心方案——从用户输入密码到权限校验，共经历四层保护：

```
用户输入密码
  │
  ├─ ① 传输层: 前端SHA-256(明文) → 网络传输只有哈希，无明文
  │
  ├─ ② 存储层: 后端SHA-256(随机盐 + 传输层摘要) → 存入Redis
  │    16字节随机盐，每个用户不同 → 相同密码产生不同哈希 → 彩虹表无效
  │
  ├─ ③ 权限表: AES-128-GCM(JSON数据) → 密文存入Redis
  │    GCM模式自带认证标签，防篡改
  │
  └─ ④ Token签名: HMAC-SHA256(username:role:timestamp, 服务端密钥)
                     → 每次请求带Token → 服务端验签放行
```

**为什么需要四层？** 如果只在数据库存哈希，中间人可以抓包看到明文密码。如果只用一层SHA-256，数据库泄露后可以直接彩虹表撞库。四层环环相扣，每一层堵上一个攻击面。

## 二、关键技术实现

### 1. 双层SHA-256密码存储

```java
// 注册时
String salt = generateRandomSalt(16);           // SecureRandom 16字节
String storedHash = SHA256(salt + transportHash); // 盐+前端哈希 → 再哈希
jedis.set("auth:user:" + username, salt + ":" + storedHash);

// 登录时
String[] parts = storedValue.split(":");
String salt = parts[0];
String expectedHash = SHA256(salt + transportHash);
if (!expectedHash.equals(parts[1])) return FAIL;
```

与普通做法对比：如果只有一层SHA-256，两个用户密码都是"123456"，数据库中的哈希完全相同 → 攻击者一眼看出。加了随机盐后，两个123456产生完全不同的哈希值。

### 2. AES-GCM 权限表加密（从ECB升级）

早期设计用了AES-ECB模式，但ECB存在同明文同密文的问题。我在第二版升级为**GCM模式**：

```java
// AES/GCM 加密
Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
byte[] iv = new byte[12]; secureRandom.nextBytes(iv);
GCMParameterSpec spec = new GCMParameterSpec(128, iv);
cipher.init(ENCRYPT_MODE, secretKey, spec);
byte[] encrypted = cipher.doFinal(jsonBytes);
// 存储: IV(12字节) + 密文 + 认证标签(16字节)
```

GCM比ECB的优势：每次加密产生不同密文（即使相同数据）、自带完整性校验标签、支持关联数据认证。如果有人在Redis中篡改了密文字节，解密时GCM会直接抛异常。

### 3. HMAC Token 签名

登录成功后不存Session，而是签发Token：

```java
String payload = username + ":" + role + ":" + System.currentTimeMillis();
String signature = HMAC_SHA256(payload, serverSecret); // 内存密钥，不落盘
String token = Base64Url(payload + ":" + signature);
```

验证时重算签名 → 一致则信任Token中的身份信息。Token被篡改 → 签名不匹配 → 拒绝请求。serverSecret在AuthServer启动时随机生成，重启即失效，杜绝长期密钥泄露风险。

### 4. 三级角色权限控制

| 角色 | 登录范围 | 核心权限 | 讲解类比 |
|------|---------|---------|---------|
| CONFIGURATOR | 仅主公机 | 全局开始/暂停/重置、用户管理 | 系统管理员 |
| OPERATOR | 任意主机 | 控制自己的车、添加新车 | 设备操作员 |
| ANALYST | 任意主机 | 只读查看、历史回放 | 数据分析师 |

配置员还加了IP白名单保护——非localhost浏览器尝试以配置员身份登录会被前端拦截+后端二次校验。

## 三、协作接口

我提供的API被Display模块直接调用：

```
POST /api/auth/register   ← Display(配置员创建用户)
POST /api/auth/login      ← Display(所有角色登录)
GET  /api/auth/verify     ← Display(WebSocket连接时验证Token)
```

WebSocket连接的首条消息必须是AUTH命令，携带Token，我验证通过后返回AUTH_OK，后续操作按角色鉴权。

---

## 四、亮点总结

1. **四层加密环环相扣**：传输→存储→权限→Token，每个环节堵一个攻击面
2. **AES-GCM替代ECB**：自带认证标签防篡改，每次加密产生不同密文
3. **无状态Token设计**：服务端不存Session，ServerSecret重启即刷新
