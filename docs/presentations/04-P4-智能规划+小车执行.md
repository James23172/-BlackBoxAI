## 一、TargetPlanner：去哪儿？——贪心目标选择

小车每次走完一段路径，首先要决定"下一个目标在哪里"。我的目标选择策略分三层：

```
① 收集候选池：扫描 mapView 位图，找出所有未探索且无碍物的格子
② 排除冲突：移除已被其他小车的target占用的格子（不抢别人的目标）
③ 贪心选择：在所有候选点中，选择距离当前位置最近的那个
    优先选取距离≤3的邻近未探索格（就近原则，节省步数）
```

**为什么用贪心不用全局最优？** 4辆小车在实时探索，地图每200ms更新一次。全局最优需要完全已知地图，而我们是未知环境——用贪心就近探索，反而比等全局最优更高效。

## 二、Navigator：怎么走？——0-1 BFS路径规划

选定目标后，我来规划实际行走路径。我实现了两种算法，支持通过配置切换。

### 2.1 BFS 0-1变体 —— 默认算法

这是核心创新。标准BFS不区分已探索和未探索的格子，但我们的场景有天然偏好——**优先走未探索区域**可以顺便扩大视野：

```
标准BFS每条边权重=1 → 所有节点平等
0-1 BFS每条边权重分两档:
  - 未探索格 → 边权重=0（优先走，"顺便探索"）
  - 已探索格 → 边权重=1（常规走）
```

实现上使用**双端队列（Deque）**：0权重的节点插头部（优先处理），1权重的插尾部：

```java
Deque<Point> queue = new ArrayDeque<>();
queue.addFirst(start);

while (!queue.isEmpty()) {
    Point cur = queue.pollFirst();
    for (int[] dir : DIRS) {
        Point next = new Point(cur.x + dir[0], cur.y + dir[1]);
        if (障碍物) continue;
        boolean isUnexplored = !explored[next.y][next.x];
        int newDist = dist[cur] + (isUnexplored ? 0 : 1);
        if (newDist < dist[next]) {
            dist[next] = newDist;
            if (isUnexplored) queue.addFirst(next);  // 优先探索
                        else   queue.addLast(next);   // 延后处理
        }
    }
}
```

效果对比：标准BFS可能绕远路走已探索的安全区域；0-1 BFS会主动穿过未探索区，走更短的直线路径，且在过程中顺便点亮地图。

### 2.2 A* 算法 —— 备选方案

也实现了标准A*，使用曼哈顿距离作为启发式函数。适用于障碍物密集、需要精确最短路径的场景。

## 三、CarAgent：小车执行三步安全机制

路径算好了，但执行才是最容易出Bug的地方。我设计了**三层安全机制**：

### 3.1 第一步：移动前障碍检查

```java
Point next = peekNextStep();
if (blackboard.isBlocked(next.x, next.y)) {
    clearRoute();                    // 清空路径
    pushTask("ROUTE_NEEDED", carId); // 重新请求规划
    return;
}
```

### 3.2 第二步：两步前瞻

这是最精妙的设计——不只检查下一步，还检查下下一步：

```java
Point next = peekNextStep();           // 第1步
Point next2 = peekNextStep(offset=1);  // 第2步（不实际弹出）
if (blackboard.isBlocked(next2) || otherCarAt(next2)) {
    clearRoute();  // 走不完 → 清空全部路径 → 重新规划
    return;
}
```

**为什么需要两步前瞻？** 如果只检查一步，小车走到障碍物前才发现走不通 → 已经浪费了一步。两步前瞻提前预判，避免"走一步卡一步"的尴尬。

### 3.3 第三步：区域点亮与即时广播

移动成功后：
```java
popNextStep();                              // 确认移动
blackboard.setCarPosition(carId, x, y);     // 更新位置
illuminator.illuminate(x, y);              // 3×3区域点亮
messageBus.fanoutPublish("REFRESH_ALL", …); // 立即刷新所有画面
```

关键设计：**移动完成后立即fanout刷新**，不等P3的200ms广播周期。这意味着移动结果约10ms内就能出现在所有显示器上。

## 四、多车协同防冲突

4辆车同时探索，最大的挑战是**避免两辆车走到同一个格子里**。我用了两种机制：

1. **目标级防冲突**：TargetPlanner分配目标时跳过其他车已占的目标
2. **路径级防冲突**：CarAgent执行两步前瞻时检查下一步是否被其他车占据

再加上P1提供的分布式锁，三管齐下保证4辆车不会"碰车"。

## 五、Illuminator：3×3区域点亮

每次小车移动一步，我点亮以新位置为中心的3×3区域：

```
移动前（●小车 @为未探索）       移动后
 @ @ @ @ @                     ░ ░ ░ @ @
 @ · · · @                     ░ ● ░ @ @     3×3区域被点亮
 @ · ● · @        →            ░ ░ ░ @ @     写入map:view位图
 @ · · · @                     @ @ @ @ @     同时从unexplored:set移除
 @ @ @ @ @                     @ @ @ @ @
```

使用Redis Pipeline批量SETBIT + SREM，9个操作用一次网络往返完成。

## 六、亮点总结

| 机制 | 设计思路 | 效果 |
|------|---------|------|
| 0-1 BFS | 未探索格边权=0，优先穿越 | 路径最短+顺便探索 |
| 两步前瞻 | 不止看下一步，还看下下一步 | 避免走一步卡一步 |
| 即时广播 | 移动后自己发fanout | 延迟<10ms，不等200ms周期 |
| Pipeline点亮 | 9次SETBIT+9次SREM一次提交 | O(1)网络往返 |
