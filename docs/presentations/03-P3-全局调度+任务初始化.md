## 一、TaskConfigurator：从零构建探索世界

当配置员在前端点下"开始"，一条`SET_CONFIG`消息就来到了我这儿。

### 1.1 网格分区出生点算法

4辆车如果全部出生在同一个位置，会相互踩踏、效率极低。我设计了一个**网格分区出生点**算法：

```
40×40地图，4辆车
cols = ceil(√4) = 2, rows = ceil(4/2) = 2
每格大小 = 20×20

┌──────────┬──────────┐
│  Car001  │  Car002  │  ← 网格(0,0)中心(10,10) 网格(1,0)中心(30,10)
│  (9,9)   │  (30,9)  │
├──────────┼──────────┤
│  Car003  │  Car004  │  ← 网格(0,1)中心(10,30) 网格(1,1)中心(30,30)
│  (9,30)  │  (30,30) │
└──────────┴──────────┘
```

每辆车分配到网格中心，并且**出生点周围3×3区域禁止生成障碍物**——保证小车出生后就能移动，不会一开始就被困住。

### 1.2 增量小车管理

探索过程中，运行员可以随时点击"添加小车"或"移除小车"。我实现了**增量操作**——不flushDB，不重建整个地图：

```java
if (addCar) {
    blackboard.addCar(carId, cx, cy);           // 新增小车，不动已有数据
    messageBus.declareQueue("Car:" + carId);     // 动态声明队列
    blackboard.pushTask("ROUTE_NEEDED", carId);  // 立即加入任务队列
}
if (removeCar) {
    blackboard.removeCar(carId);                 // 移除，不影响其他车
}
```

### 1.3 崩溃恢复

如果Controller意外崩溃，重启后地图不需要重新初始化。我引入了`forceReset`标志：
- 检测到已有配置且forceReset=false → **跳过初始化**，直接复用现有地图
- 触发Redis BGSAVE持久化，确保崩溃后数据不丢失

## 二、ControllerAgent：双线程调度引擎

这是我设计的核心——一个**拉式任务驱动**的调度器。

### 2.1 双线程架构

```
Thread-1: taskProcessor             Thread-2: broadcastScheduler
┌──────────────────────┐          ┌──────────────────────┐
│ BLPOP taskQueue 阻塞  │          │ 每200ms一次循环       │
│   ↓ 取出任务          │          │   ├─ 收集所有车状态    │
│ 解析任务类型:          │          │   ├─ 写入Redis        │
│  ROUTE_NEEDED?        │          │   └─ fanoutPublish    │
│    → NAVIGATE到Nav    │          │      "REFRESH_ALL"    │
│  MOVE_READY?          │          └──────────────────────┘
│    → MOVE_STEP到Car   │
│  BLOCKED?             │
│    → 重置状态 → 重新   │
│  TASK_COMPLETE?       │
│    → 停止调度          │
└──────────────────────┘
```

广播线程独立于任务线程，确保即使任务处理繁忙，画面也能保持流畅的200ms刷新。

### 2.2 拉式任务状态机

这是整个系统最核心的设计——**任务状态机**：

```
ROUTE_NEEDED ──→ Controller发出NAVIGATE ──→ Navigator/TargetPlanner处理
                                                    │
                                                    ↓
MOVE_READY   ←── Navigator规划完毕 ←── pushTask回taskQueue
    │
    ├─→ Controller发出MOVE_STEP → Car执行移动
    │
    └─→ Car移动完毕 → pushTask(ROUTE_NEEDED) → 循环
```

**为什么用拉式不用推式？** 推式需要Controller知道每个模块的地址和状态，耦合严重。拉式模式下，Controller只需从taskQueue中BLPOP取任务，谁放进去的、怎么处理的——Controller完全不用关心。这是黑板架构的精髓。

### 2.3 配置员/运行员双层暂停控制

```java
// 配置员点"全局暂停" → Controller.taskActive = false
//   → taskProcessor线程 wait() 休眠
//   → 所有小车停止移动
//   → 运行员的"开始"按钮变灰

// 运行员点"暂停我的车"  
//   → 仅该Car不消费MOVE_STEP消息
//   → 其他运行员的小车不受影响
```

这个设计的关键：配置员的权限覆盖运行员，但运行员之间互不影响。

## 三、协作接口

| 上游 | 消息 | 我的处理 |
|------|------|---------|
| Display(前端) | SET_CONFIG / RESET | FORWARD_CONFIG到TaskConfigurator |
| 各模块 | pushTask到taskQueue | BLPOP消费，类型分派 |

| 下游 | 消息 | 触发条件 |
|------|------|---------|
| Navigator | NAVIGATE | ROUTE_NEEDED |
| Car | MOVE_STEP | MOVE_READY |
| Display | REFRESH_ALL (Fanout) | 每200ms |

---

## 四、亮点总结

1. **拉式任务队列解耦**：Controller不感知任何下游模块，只从Redis BLPOP取任务、发命令
2. **网格分区出生点**：√N分区算法保4辆车各占一个象限，初始分散度最大化
3. **双层暂停权限**：配置员全局冻结 + 运行员个人暂停，权限层级清晰
