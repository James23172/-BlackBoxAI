# 第一部分：整体框架思路

## 1.1 项目是什么？解决什么问题？

### 生活类比：一群清洁工扫楼

想象你是一栋办公楼的管理员，有 4 个清洁工。你的任务是让他们**在最短时间内把整栋楼的所有房间都打扫一遍**，但问题是：
- 你不知道哪些房间已经打扫过、哪些没打扫过
- 你不知道哪些房间里有障碍物（比如堆满了箱子进不去）
- 你不能让两个清洁工同时去打扫同一个房间（浪费人力）
- 清洁工之间不能直接交流

**BlackBoxAI 就是来解决这个问题的**。它用 4 辆"小车"（清洁工）在 40×40 的方格地图（办公楼）上移动，把每个格子都"探索"（打扫）一遍。

### 为什么不简单点？

你可能会问："直接给每辆车分配一块区域不就行了吗？"

问题在于：
1. **地图上有随机障碍物**（10% 概率），车不能预测哪里会被堵住
2. **车只能看到周围 3×3 的区域**，不知道远处的情况
3. **4 辆车需要协同**，避免重复探索同一区域
4. **系统需要支持多台电脑同时运行**，一个控制中心 + 多个操作终端

所以这不是一个简单的"分蛋糕"问题，而是一个**分布式多机器人协同探索**问题——这是机器人学中的经典难题。

## 1.2 核心设计理念：黑板模式 + C2 架构

### 黑板模式（Blackboard Pattern）

想象你小时候教室里的黑板：
- 老师在黑板上写题目
- 每个学生都可以看黑板上的题目
- 学生做完题后把答案写在黑板上
- 老师和其他学生都可以看到

**Redis 就是我们系统的"黑板"**：
- 所有模块（车、导航器、控制器）都**只能**通过读写 Redis 来交换信息
- 没有任何两个模块直接对话（不直接调用对方的方法）
- 好处：模块之间完全解耦，一个模块挂了不影响其他模块

```
                    ┌─────────────────────────┐
                    │      Redis（黑板）        │
                    │                         │
                    │  map:view    → 哪些格子   │
                    │              已探索？    │
                    │  map:blocked → 哪些格子   │
                    │              有障碍物？  │
                    │  car:001:position → 车在 │
                    │              哪里？      │
                    │  taskQueue   → 待办任务   │
                    │              列表        │
                    └───────┬─────┬─────┬─────┘
                            │     │     │
                     ┌──────┘     │     └──────┐
                     ▼            ▼            ▼
                 Controller   Navigator     Car
                 (看黑板)     (看黑板)     (看黑板)
```

### C2 架构（Command and Control）

C2 源自军事指挥体系，核心思想是：
- **Controller 是唯一的大脑**，负责下达所有命令
- **其他模块是被动执行者**，只响应命令，不主动行动
- **Controller 自己不干活**（不移动车、不规划路径），只做决策

```
           ┌──────────────────┐
           │    Controller    │  ← 唯一的大脑
           │    (全局调度器)    │
           └──┬───┬───┬───┬──┘
              │   │   │   │
        ┌─────┘   │   │   └─────┐
        ▼         ▼   ▼         ▼
    Navigator    Car  Car     TaskConfig
    (路径规划)  (移动)(移动)   (初始化)
```

### 为什么用这两个模式？

| 设计目标 | 黑板模式如何满足 | C2 架构如何满足 |
|---------|----------------|----------------|
| 模块独立 | 只通过 Redis 读写，不改对方代码 | 模块只收命令不主动行动 |
| 容易扩展 | 新模块只需读写 Redis 即可加入 | 新模块只需订阅队列 |
| 避免冲突 | 通过分布式锁控制并发写入 | Controller 统一调度 |
| 容错恢复 | Redis 持久化，重启可恢复 | Controller 崩溃恢复 |

## 1.4 消息流转概览

系统的核心工作流可以用一个完整的"任务生命周期"来描述。从用户点击"开始"到地图被完全探索，经历了以下步骤：

```
Step 1: 用户在前端点击"应用配置"
  Display → Redis taskQueue (SET_CONFIG)

Step 2: Controller 从 taskQueue 拉取 SET_CONFIG
  Controller → RabbitMQ TaskConfigCmd (FORWARD_CONFIG)

Step 3: TaskConfigurator 收到 FORWARD_CONFIG
  ① clearAll() 清空 Redis
  ② 初始化地图 (40×40)
  ③ 生成 10% 随机障碍物
  ④ 放置 4 辆小车到网格分区出生点
  ⑤ 为每辆车创建 ROUTE_NEEDED 任务 → taskQueue
  ⑥ 声明所有 RabbitMQ 队列

Step 4: 用户点击"开始"
  Display → Redis taskQueue (START)

Step 5: Controller 拉取 START
  → setTaskActive(true)
  → Controller 开始处理 taskQueue 中的 ROUTE_NEEDED

Step 6: Controller 处理 ROUTE_NEEDED
  → 发 NAVIGATE → RabbitMQ Navigator4CarID

Step 7: Navigator 收到 NAVIGATE
  → 发 GET_TARGET → RabbitMQ TargetPlannerCmd

Step 8: TargetPlanner 收到 GET_TARGET
  → 从 unexplored:set 随机选最近未探索格
  → 写入 car:{id}:target (Redis)
  → 发 ROUTE_NEEDED → taskQueue

Step 9: Controller 再次处理 ROUTE_NEEDED
  → 发 NAVIGATE → RabbitMQ Navigator4CarID

Step 10: Navigator 再次收到 NAVIGATE
  → 从 Redis 读起点、目标、障碍物
  → BFS/A* 规划路径
  → 写入 car:{id}:route (Redis)
  → 发 MOVE_READY → taskQueue

Step 11: Controller 处理 MOVE_READY
  → 暂停检查（全局/个人）
  → 发 MOVE_STEP → RabbitMQ Car:{id}

Step 12: Car 收到 MOVE_STEP
  → 两步前瞻检查
  → 移动、3×3 点亮
  → 即时广播 REFRESH_ALL
  → 路径走完 → 发 ROUTE_NEEDED → taskQueue

循环 Step 6-12，直到 unexplored:set 为空 → 巡检完成！
```

# 第二部分：九大模块核心详解

## 2.1 common — 公共基础设施

**角色**：整个系统的"地基"，其他 8 个模块都依赖它。

### 包含的核心类

| 类名 | 作用 | 类比 |
|------|------|------|
| `ConfigConstants` | 全局常量（IP、端口、队列名、Key 名） | 公司规章制度手册 |
| `BlackboardClient` | Redis 读写封装（黑板唯一入口） | 黑板前的粉笔和板擦 |
| `MessageBusClient` | RabbitMQ 收发封装 | 对讲机 |
| `DistributedLock` | 分布式锁（防并发冲突） | 厕所门锁 |
| `ArgsParser` | 命令行参数解析 | 遥控器按钮 |
| `Launcher` | 一键启动所有模块 | 汽车的总开关 |
| `Point` | 坐标模型 (x, y) | 门牌号 |
| `CarState` | 小车状态模型 | 体检报告 |
| `MQMessage` | 消息模型 | 信封 |
| `CarStatus` | 小车状态枚举 (IDLE/MOVING/BLOCKED) | 交通信号灯 |
| `CommandType` | 命令类型枚举 (NAVIGATE/MOVE_STEP/...) | 军令类型 |

### 关键设计决策

**为什么用 Redis 作为黑板？**
- Redis 是内存数据库，读写速度极快（微秒级）
- Redis 的 BIT 操作天然适合存储 40×40=1600 个格子的探索状态（每个 bit = 1 格）
- Redis 的 List 天然适合实现 FIFO 任务队列
- Redis 的 SET 天然适合存储"未探索格子集合"
- 支持持久化（RDB 快照），崩溃后可恢复

**为什么用 RabbitMQ 作为消息总线？**
- RabbitMQ 支持多个消费者竞争同一个队列（Navigator 可以横向扩展）
- RabbitMQ 支持 Fanout Exchange（广播给所有 Display，实现毫秒级画面同步）
- 消息持久化到磁盘，不怕宕机

## 2.2 auth — 认证鉴权系统

**角色**：系统的门卫，决定谁能进、能做什么。

### 三级角色

| 角色 | 权限 |
|------|------|
| **配置员** (configurator) | 一切权力：配置地图、启停任务、添加/删除车、编辑障碍物、录制回放 |
| **运行员** (operator) | 只能启停自己归属的车、查看全局状态 |
| **分析员** (analyst) | 只能查看、播放回放 |

### 四层加密体系

```
用户输入密码 "123456"
     │
     ▼
第一层（前端传输加密）
  SHA-256("123456") → "8d969eef6ecad3c29a3a629280e686cf0c3f5d5a86aff3ca12020c923adc6c92"
     │  通过 HTTPS/WebSocket 传输
     ▼
第二层（存储加密）
  随机 16 字节 salt + SHA-256(salt + 前端传来的hash)
  → "abc123...:def456..."  (salt:hash 格式存入 Redis)
     │
     ▼
第三层（权限表加密）
  权限矩阵 → JSON → AES-GCM 加密 → 存入 Redis auth:permissions
     │
     ▼
第四层（Token 认证）
  登录成功后 → HMAC-SHA256("username:role:过期时间") → 24 小时有效
  每次操作都带 Token 验证
```

## 2.5 navigator — 路径规划器

**角色**：地图导航软件（就像手机上的高德地图），为小车规划从 A 到 B 的最短路径。

### 核心算法：0-1 BFS

普通 BFS 走一步代价都是 1。但我们的需求是：**优先走未探索区域**。

0-1 BFS 的巧妙之处：
- 走向**未探索**的格子：代价 = 0（优先走）→ 放入双端队列**头部**
- 走向**已探索**的格子：代价 = 1（不优先）→ 放入双端队列**尾部**

这样算法会"贪心"地优先穿过未探索区域，同时保证整体路径最短。

### 备选算法：A*

使用曼哈顿距离作为启发函数：`h = |x1-x2| + |y1-y2|`，可以更快找到路径但未必优先走未探索区。

### 关键流程

```
收到 NAVIGATE(carId)
  │
  ├─ 从 Redis 读 car:{carId}:position → 起点
  ├─ 从 Redis 读 car:{carId}:target → 目标
  │
  ├─ 如果目标不存在
  │    └─ 发 GET_TARGET → TargetPlannerCmd（让目标选择器选目标）
  │
  ├─ 如果目标存在
  │    ├─ 从 Redis 读 map:blocked → 障碍物 bitmap
  │    ├─ 从 Redis 读 map:view → 探索 bitmap
  │    ├─ 调用 BFS/A* 规划路径
  │    ├─ 写入 car:{carId}:route → Redis List（路径点序列）
  │    ├─ 设置 car 状态为 IDLE
  │    └─ 发 MOVE_READY → taskQueue（告诉 Controller：路径已就绪）
  │
  └─ 如果路径规划失败（目标不可达）
       └─ 清除目标、重新入队 ROUTE_NEEDED
```

## 2.6 target-planner — 目标选择器

**角色**：侦察兵，告诉小车"下一个应该去哪"。

### 贪心最近格策略

```
收到 GET_TARGET(carId)
  │
  ├─ 从 Redis 读 car:{carId}:position → 当前位置
  │
  ├─ 从 Redis 读 unexplored:set → 所有未探索坐标
  │    （SRANDMEMBER 随机获取，O(1) 时间复杂度）
  │
  ├─ 排除其他车已经"认领"的目标
  │
  ├─ 贪心选择：
  │    优先：距离 ≤ 3 的最近未探索格
  │    其次：全局距离最近的未探索格
  │
  └─ 写入 car:{carId}:target → Redis
      发送 ROUTE_NEEDED → taskQueue
```

为什么是"贪心"？因为每次都选当前最近的未探索格，不保证全局最优，但在实践中效果很好，且计算开销极小。

## 2.7 car — 小车执行器

**角色**：清洁工本人，收到命令后实际移动。

### 两步前瞻机制

这是 Car 模块最精妙的设计。小车在移动前不仅检查下一步，还检查第二步：

```
1. peekNextStep() 查看路径上的下一步
   │
   ├─ 路径为空 → handleRouteDone()
   │    └─ 设为 IDLE，发 ROUTE_NEEDED → taskQueue
   │
   ├─ 下一步有障碍物 → handleBlocked()
   │    └─ 设为 BLOCKED，记录受阻 tick，发 BLOCKED → taskQueue
   │
   └─ 下一步可走 →
        │
        ├─ popNextStep() 弹出下一步（消费路径）
        ├─ 更新位置到 Redis
        ├─ 3×3 illuminateArea() 点亮周围
        ├─ 递增步数
        │
        ├─ 两步前瞻：peek 第二步
        │    ├─ 第二步有障碍 → 清空剩余路径 → handleRouteDone
        │    └─ 第二步合法 → 设为 IDLE，等待下一个 MOVE_STEP
        │
        └─ 即时广播 REFRESH_ALL（不等 100ms 周期）
```

**为什么需要两步前瞻？**
如果只检查一步，车走了第一步才发现第二步是障碍物，那就白白浪费了一步。两步前瞻相当于"看到前面有坑就提前绕路"。

### 3.2.2 RabbitMQ 概念对照

| RabbitMQ 概念 | 解释 | 在项目中的体现 |
|---------------|------|---------------|
| **Queue（队列）** | 消息的管道，先进先出 | `Navigator4CarID`、`Car:Car001` |

### 3.2.3 关键设计模式

**拉式任务驱动（Pull-based Task Queue）**

不要与"推式"混淆：
- **推式**：老板不停给你派活（你没法拒绝）
- **拉式**：任务板上贴任务，你主动去领取（可以控制节奏）

Controller 使用**拉式**：通过 Redis List 的 BLPOP 阻塞等待任务，自己能控制处理速度。

```
推式: Controller 订阅 N 个队列，消息不断涌入 → 可能过载
拉式: Controller BLPOP 阻塞等任务 → 处理完一个再拉下一个 → 不会过载
```

```java
        String message = new String(delivery.getBody(), StandardCharsets.UTF_8);

            handleForwardConfig(message);  // 核心处理逻辑
        } catch (Exception e) {
            LOG.error("处理消息失败: {}", message, e);
        } finally {
            channel.basicAck(delivery.getEnvelope().getDeliveryTag(), false);  // 手动确认
        }
    };
    channel.basicConsume(TASK_CONFIG_QUEUE, false, deliverCallback, consumerTag -> {});
```

**逐行讲解**：

| 代码 | 含义 |
|------|------|
| `DeliverCallback` | Java 的 lambda 表达式，定义"收到消息后做什么"的回调函数 |
| `new String(delivery.getBody(), StandardCharsets.UTF_8)` | 把 RabbitMQ 收到的字节数组转换成 UTF-8 编码的字符串 |
| `handleForwardConfig(message)` | 调用核心逻辑处理消息 |
| `channel.basicAck(...)` | 手动确认消息已处理。`false` 表示只确认这一条（不批量确认） |
| `channel.basicConsume(TASK_CONFIG_QUEUE, false, ...)` | 开始消费队列。`false` 表示**手动确认**模式 |

**为什么用手动确认而非自动确认？**
自动确认意味着 RabbitMQ 一把消息发给你就算"已处理"了。但如果你的程序在处理消息的时候崩溃了，这条消息就丢了。手动确认意味着只有在你成功处理完消息后才告诉 RabbitMQ "我处理好了"，如果崩溃了，RabbitMQ 会把消息发给其他消费者重试。

**生活类比**：手动确认就像签收快递。自动确认是快递员把包裹扔门口就走（可能被人拿走）；手动确认是你签了字快递员才走（确保东西到你手上）。

### 3.3.7 computeSpawnPoints() — 网格分区出生点算法

```java
private List<Point> computeSpawnPoints(int mapWidth, int mapHeight, int carCount) {
    if (carCount <= 0) return new ArrayList<>();

    // 计算网格布局：cols = ceil(sqrt(N)), rows = ceil(N / cols)
    int cols = (int) Math.ceil(Math.sqrt(carCount));
    int rows = (int) Math.ceil((double) carCount / cols);
    int cellW = mapWidth / cols;
    int cellH = mapHeight / rows;
```

**算法讲解**：

假设 4 辆车：
```
Math.sqrt(4) = 2.0 → cols = 2, rows = ceil(4/2) = 2
→ 2×2 网格，每格 40/2 = 20×20

┌──────────┬──────────┐
│  Car001  │  Car002  │
│  (10,10) │  (30,10) │
├──────────┼──────────┤
│  Car003  │  Car004  │
│  (10,30) │  (30,30) │
└──────────┴──────────┘
```

假设 5 辆车：
```
Math.sqrt(5) ≈ 2.236 → cols = 3, rows = ceil(5/3) = 2
→ 3 列 × 2 行 = 6 格，但只用前 5 格

┌─────────┬─────────┬─────────┐
│ Car001  │ Car002  │ Car003  │
│ (6,10)  │ (20,10) │ (34,10) │
├─────────┼─────────┼─────────┤
│ Car004  │ Car005  │  (空)   │
│ (6,30)  │ (20,30) │         │
└─────────┴─────────┴─────────┘
```

```java
    List<Point> spawns = new ArrayList<>();
    int idx = 0;
    for (int row = 0; row < rows && idx < carCount; row++) {
        for (int col = 0; col < cols && idx < carCount; col++) {
            // 格子中心作为出生点
            int cx = col * cellW + cellW / 2;
            int cy = row * cellH + cellH / 2;
            // 确保在边界内（离边缘至少 1 格）
            cx = Math.max(1, Math.min(mapWidth - 2, cx));
            cy = Math.max(1, Math.min(mapHeight - 2, cy));
            spawns.add(new Point(cx, cy));
            idx++;
        }
    }
    return spawns;
}
```

**边界保护讲解**：
- `Math.max(1, ...)`：确保出生点不会太靠左/上（x 至少为 1）
- `Math.min(mapWidth - 2, ...)`：确保出生点不会太靠右/下（x 最多为 mapWidth-2）
- 为什么要留边距？因为小车需要 3×3 的活动空间，太靠边可能出界。

**为什么用网格分区而不是随机放置？**
随机放置可能导致车扎堆（比如 4 辆车都随机到地图左上角），它们会互相竞争同一片区域的未探索格子，降低整体效率。网格分区保证车分散在不同区域，各自独立探索。

### 3.3.8 buildForbiddenZone() — 禁区构建

```java
private Set<Point> buildForbiddenZone(List<Point> spawnPoints, int mapWidth, int mapHeight) {
    Set<Point> forbidden = new HashSet<>();
    for (Point spawn : spawnPoints) {
        for (int dy = -1; dy <= 1; dy++) {
            for (int dx = -1; dx <= 1; dx++) {
                int nx = spawn.x + dx;
                int ny = spawn.y + dy;
                if (nx >= 0 && nx < mapWidth && ny >= 0 && ny < mapHeight) {
                    forbidden.add(new Point(nx, ny));
                }
            }
        }
    }
    LOG.info("禁区集合: {} 个出生点, {} 个禁止放置格", spawnPoints.size(), forbidden.size());
    return forbidden;
}
```

**讲解**：

对于每个出生点 (cx, cy)，将其周围 3×3 区域标记为禁区：

```
        ┌─────┬─────┬─────┐
        │(x-1,│(x,  │(x+1,│
        │y-1) │y-1) │y-1) │
        ├─────┼─────┼─────┤
        │(x-1,│(x,y)│(x+1,│  ← 出生点居中
        │y)   │ ★   │y)   │
        ├─────┼─────┼─────┤
        │(x-1,│(x,  │(x+1,│
        │y+1) │y+1) │y+1) │
        └─────┴─────┴─────┘
```

**为什么需要禁区？**
如果障碍物生成在出生点旁边，车一出生就被困住了！禁区确保车至少有一个安全的出生环境。

注意双重循环的边界检查：
- `dy = -1, 0, 1`（从上到下）
- `dx = -1, 0, 1`（从左到右）
- `if (nx >= 0 && nx < mapWidth && ny >= 0 && ny < mapHeight)`：确保禁区格在地图范围内

### 3.3.9 generateObstacles() — 障碍物随机生成

```java
private int generateObstacles(int mapWidth, int mapHeight,
                               double obstacleDensity, Set<Point> forbidden) {
    int totalCells = mapWidth * mapHeight;
    int targetObstacleCount = (int) (totalCells * obstacleDensity);

    int placed = 0;
    int maxAttempts = targetObstacleCount * 20;  // 最多尝试 20 倍目标数量
    int attempts = 0;
    java.util.List<Point> obstacles = new java.util.ArrayList<>();

    while (placed < targetObstacleCount && attempts < maxAttempts) {
        int x = random.nextInt(mapWidth);
        int y = random.nextInt(mapHeight);
        Point p = new Point(x, y);
        attempts++;

        if (!forbidden.contains(p) && !blackboard.isBlocked(x, y)) {
            obstacles.add(p);
            placed++;
        }
    }
```

**逐行讲解**：

| 代码 | 含义 |
|------|------|
| `totalCells * obstacleDensity` | 40×40=1600 × 0.1 = **160 个目标障碍物** |
| `maxAttempts = targetObstacleCount * 20` | 最多尝试 3200 次。为什么？因为随着放置增多，重复概率增大，需要足够多尝试 |
| `random.nextInt(mapWidth)` | 生成 [0, 39] 的随机整数 |
| `!forbidden.contains(p)` | 不在禁区内 |
| `!blackboard.isBlocked(x, y)` | 该位置还没有障碍物（GETBIT O(1) 检查） |

```java
    if (placed < targetObstacleCount) {
        LOG.warn("障碍物生成不足: 目标={}, 实际={}", targetObstacleCount, placed);
    }

    // Pipeline 批量写入所有障碍物
    blackboard.setBlockedBatch(obstacles);
    LOG.info("已生成 {} 个障碍物 (目标: {})", placed, targetObstacleCount);
    return placed;
}
```

**`setBlockedBatch()` 为什么用 Pipeline？**

如果不用 Pipeline：
```
for (Point p : obstacles) {
    blackboard.setBlocked(p.x, p.y);  // 每次一个网络往返
}
// 160 个障碍物 = 160 次网络往返，假设每次 0.5ms = 80ms
```

用 Pipeline：
```
Pipeline pipeline = jedis.pipelined();
for (Point p : obstacles) {
    pipeline.setbit("map:blocked", offset, true);  // 先攒着不发
    pipeline.srem("unexplored:set", p.x + "," + p.y);
}
pipeline.sync();  // 一次性发送全部命令 = 1 次网络往返
// 1 次网络往返 ≈ 0.5ms → 快 160 倍！
```

**生活类比**：Pipeline 就像你写了 10 封信，不用跑 10 趟邮局，而是装在一个大信封里寄一次。

### 3.4.2 ControllerAgent 类结构总览

```java
public class ControllerAgent {
    // === 核心依赖 ===
    private final BlackboardClient bb;       // Redis 黑板
    private final MessageBusClient mq;       // RabbitMQ 消息总线

    // === 双线程架构 ===
    private final ScheduledExecutorService broadcastScheduler;  // 定时广播线程（每 100ms）
    private Thread taskProcessor;             // 任务处理线程

    // === 状态变量 ===
    private final int instanceId;             // 实例编号（多实例分片）
    private final int totalInstances;         // 总实例数
    private volatile boolean running = false; // 是否运行中
    private volatile boolean taskActive = false;   // 任务是否激活
    private volatile boolean userActivated = false; // 用户是否点击了开始
    private long tickCount = 0;               // 节拍计数器
    private volatile boolean recording = false; // 是否录制快照

    // === 并发控制 ===
    private final Object taskWakeLock = new Object();  // 任务线程的"闹钟"
}
```

**`volatile` 关键字讲解**：
在多线程环境下，一个线程修改了变量的值，另一个线程可能看不到（因为 CPU 缓存）。`volatile` 保证所有线程都能看到最新的值。这里 `running`、`taskActive` 等被多个线程读写，所以必须用 `volatile`。

**`final Object taskWakeLock` 讲解**：
这是一个 Java 并发原语——作为"等待/通知"的锁对象。就像你等外卖时给快递员一个门牌号（`taskWakeLock`），他到了就按门铃（`notifyAll`）通知你。

### 3.4.3 start() 方法 — 启动双线程

```java
public void start() {
    running = true;
    // 清除上次运行残留的活跃状态（防止崩溃后重启的脏数据）
    bb.setTaskActive(false);
    bb.clearTaskQueue();

    // 启动事件驱动任务处理线程（BLPOP 阻塞等待 Redis taskQueue）
    taskProcessor = new Thread(this::taskProcessLoop, "controller-task-processor");
    taskProcessor.setDaemon(true);  // 守护线程
    taskProcessor.start();

    // 启动周期性广播调度器（每 100ms 刷新 Display）
    broadcastScheduler.scheduleAtFixedRate(this::broadcastTick,
            ConfigConstants.TICK_INTERVAL_MS, ConfigConstants.TICK_INTERVAL_MS, TimeUnit.MILLISECONDS);

    log.info("Controller 已启动: 纯 Redis taskQueue 驱动 + {}ms 周期性广播", ConfigConstants.TICK_INTERVAL_MS);
}
```

**为什么清除残留状态？**
假设上次运行 Controller 崩溃了（没有执行 `stop()`），Redis 中可能残留 `taskActive=true`。如果不清理，新 Controller 启动后会以为自己应该处理任务，但实际上没有配置。

**守护线程（Daemon Thread）讲解**：
守护线程是"主线程结束我也结束"的线程。如果 `main` 方法结束，守护线程自动终止。这样当程序关闭时，不会因为任务处理线程没退出而导致 JVM 无法退出。

**`scheduleAtFixedRate` 参数详解**：
```
scheduleAtFixedRate(
    this::broadcastTick,  // 要执行的方法
    100,                  // 首次延迟（ms），立即开始第一次
    100,                  // 周期（ms），每 100ms 执行一次
    TimeUnit.MILLISECONDS // 时间单位
)
```

**双线程架构图示**：

```
Controller 启动
    │
    ├── 线程 1：taskProcessor（任务处理线程）
    │   ├── 状态：BLPOP 阻塞等待
    │   ├── 触发：taskQueue 有新任务
    │   └── 工作：拉取任务 → 处理 → 分发命令
    │
    └── 线程 2：broadcastScheduler（周期性广播线程）
        ├── 状态：每 100ms 自动执行
        ├── 触发：定时器
        └── 工作：
            ├── 检查探索是否完成
            ├── 驱动空闲小车
            ├── 兜底检查受阻车
            ├── 录制快照
            └── 广播 REFRESH_ALL
```

### 3.4.4 taskProcessLoop() — 任务处理主循环

这是 Controller 最核心的方法，理解它就理解了整个调度器。

```java
private void taskProcessLoop() {
    log.info("任务处理线程启动 (纯 Redis BLPOP), taskActive={}", taskActive);
    while (running) {  // 只要 Controller 在运行就一直循环
        try {
            // ── 第一阶段：等待激活 ──
            if (!taskActive) {
                synchronized (taskWakeLock) {
                    if (!taskActive && running) {
                        taskWakeLock.wait(1000);  // 等待 1 秒（超时唤醒）
                    }
                }
                // 每次超时唤醒后也检查 Redis 中的 taskActive
                // 允许 Display 通过 Redis 唤醒 Controller
                if (!taskActive && running) {
                    try {
                        boolean redisActive = bb.isTaskActive();
                        if (redisActive) {
                            log.info("检测到 Redis taskActive=true, 激活任务处理器");
                            taskActive = true;
                        }
                    } catch (Exception e) { /* ignore, will retry next cycle */ }
                }
                continue;  // 回到循环开头
            }

            // ── 第二阶段：拉取并处理任务 ──
            Map<String, String> task = bb.blockingPopTask(2);
            if (task != null) {
                processTask(task);
                // 连续清空剩余任务（处理一条后如果还有就继续，避免积压）
                Map<String, String> next;
                while ((next = bb.popTask()) != null) {
                    processTask(next);
                }
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            break;
        } catch (Exception e) {
            log.error("任务处理异常", e);
            try { Thread.sleep(500); } catch (InterruptedException ie) { ... }
        }
    }
    log.info("任务处理线程退出");
}
```

**分段讲解**：

**第一阶段：等待激活**

```
taskActive = false（初始状态）

  while(running) {
      if (!taskActive) {
          wait(1000);              ← 线程睡 1 秒
          检查 Redis taskActive;   ← 可能是 Display 通过 Redis 激活的
          continue;                ← 回到循环开头，再检查 taskActive
      }
      ...
  }
```

这种模式叫"轮询 + 事件驱动"：
- **轮询**：每 1 秒醒来检查一次 Redis
- **事件驱动**：Display 写入 Redis `config:task taskActive=1` 后，Controller 在下一个轮询周期检测到

**为什么不用更快的轮询（比如 100ms）？**
`wait(1000)` 已经够快了（用户点击"开始"到 Controller 响应最多 1 秒），而且不消耗 CPU。如果用 10ms 轮询，CPU 会一直忙等，浪费资源。

**第二阶段：拉取并处理任务**

```java
Map<String, String> task = bb.blockingPopTask(2);  // BLPOP 阻塞 2 秒等任务
```

`BLPOP taskQueue 2` 的含义：
- 如果 taskQueue 有元素 → 立即弹出并返回（和 LPOP 一样）
- 如果 taskQueue 是空的 → 阻塞等待最多 2 秒
- 如果 2 秒内没有新元素 → 返回 null

**为什么要连续清空剩余任务？**
```
while ((next = bb.popTask()) != null) {
    processTask(next);
}
```

假设在处理一条 ROUTE_NEEDED 的过程中，Navigator 完成了路径规划并推入了 MOVE_READY。如果不连续清空，MOVE_READY 要等到下一轮 BLPOP 才会被处理。连续清空确保了任务不积压。

**生活类比**：
- `BLPOP` 2 秒阻塞 = 你叫号排队，最多等 2 分钟，没人叫你就回家
- 连续清空 = 你办完一件事后，不离开柜台，继续问"还有事吗？还有事吗？"直到没人排队

### 3.4.5 processTask() — 任务分发

```java
private void processTask(Map<String, String> task) {
    String type = task.get("type");
    String carId = task.get("carId");

    // 全局任务（无 carId）
    switch (type) {
        case "START":        handleStartTask();     return;
        case "PAUSE":        handlePauseTask();     return;
        case "SET_CONFIG":   handleSetConfigTask(task);  return;
        case "RESET":        handleResetTask(task);      return;
        case "RECORD_START": recording = true;           return;
        case "RECORD_STOP":  recording = false;          return;
    }

    // 车辆相关任务
    if (carId == null) {
        log.warn("taskQueue 任务缺少 carId: {}", task);
        return;
    }

    // 多实例分片：只处理分配给本实例的车辆
    if (!isMyCar(getAllCarIds(), carId)) return;

    switch (type) {
        case "ROUTE_NEEDED":
            requestNavigate(carId);  // 发 NAVIGATE → Navigator4CarID
            break;

        case "MOVE_READY":
            // 暂停检查
            if (bb.isGlobalPaused()) { log.debug("全局暂停中，跳过"); break; }
            String owner = bb.getCarOwner(carId);
            if (owner != null && !owner.isEmpty() && bb.isOperatorPaused(owner)) {
                log.debug("运行员 {} 暂停中，跳过", owner);
                break;
            }
            // 发 MOVE_STEP → Car:{id}
            JSONObject moveData = new JSONObject();
            moveData.put("carId", carId);
            sendCommand(CommandType.MOVE_STEP, moveData, ConfigConstants.carQueueName(carId));
            break;

        case "ADD_CAR":
            requestNavigate(carId);  // 新增小车也触发导航
            break;

        case "BLOCKED":
            handleBlockedTimeout(carId);  // 超时处理
            break;
    }
}
```

**双层暂停检查（重点！）**：

```
MOVE_READY 处理时的暂停检查链路：

if (bb.isGlobalPaused())          ← 第 1 层：全局暂停（配置员）
    → 跳过，不发 MOVE_STEP

if (bb.isOperatorPaused(owner))   ← 第 2 层：个人暂停（运行员）
    → 跳过，不发 MOVE_STEP

否则 → 正常发 MOVE_STEP
```

**为什么是两层？**
- **全局暂停**：配置员按下"全局暂停"，所有车都停
- **个人暂停**：运行员 A 按下暂停，只有他负责的车停（运行员 B 的车继续跑）

这就像教室里的纪律：
- 校长说"全校停课" → 所有班级停课（全局暂停）
- 班主任说"我们班自习" → 只有这个班停课（个人暂停）

### 3.4.6 handleStartTask() — 启动任务

```java
private void handleStartTask() {
    Map<String, String> existingConfig = blackboard.getTaskConfig();
    boolean hasConfig = existingConfig != null && !existingConfig.isEmpty();

    if (!hasConfig) {
        // 从未初始化过 → 触发完整初始化
        log.warn("配置不存在，触发完整初始化");
        userActivated = true;
        JSONObject initData = new JSONObject();
        initData.put("mapWidth", bb.getMapWidth());
        initData.put("mapHeight", bb.getMapHeight());
        initData.put("carCount", Math.max(4, bb.getAllCarIds().size()));
        initData.put("obstacleDensity", ConfigConstants.DEFAULT_OBSTACLE_DENSITY);
        initData.put("routeAlgorithm", getRouteAlgorithm());
        initData.put("active", true);  // ← 初始化完成后立即激活
        taskActive = false;
        sendCommand(CommandType.FORWARD_CONFIG, initData, ConfigConstants.QUEUE_TASK_CONFIG_CMD);
    } else {
        // 配置已存在 → 直接激活
        userActivated = true;
        bb.setTaskActive(true);
        taskActive = true;
        wakeTaskProcessor();  // 唤醒 BLPOP 等待中的 taskProcessLoop
    }
    recording = true;  // 自动开始录制快照
}
```

**两个分支讲解**：

**分支 1：配置不存在（首次使用）**
```
用户直接点"开始"（没先点"应用配置"）
  → Controller 发现 Redis 中 config:task 为空
  → Controller 代替用户自动生成默认配置
  → 发送 FORWARD_CONFIG(active=true) 给 TaskConfigurator
  → TaskConfigurator 初始化完成后直接激活任务
```

这就是为什么即使用户不先点"应用配置"、直接点"开始"，系统也能正常工作。

**分支 2：配置已存在（正常流程）**
```
用户先点了"应用配置"（TaskConfigurator 已初始化）
  再点"开始" → Controller 发现 config:task 不为空
  → 直接 setTaskActive(true)
  → wakeTaskProcessor() 唤醒任务处理线程
  → taskProcessLoop 开始处理 taskQueue 中的 ROUTE_NEEDED
```

**`wakeTaskProcessor()` 为什么必要？**

回想 `taskProcessLoop` 的代码：
```java
if (!taskActive) {
    synchronized (taskWakeLock) {
        taskWakeLock.wait(1000);  // 线程正在睡！
    }
}
```

如果不调用 `wakeTaskProcessor()`，taskProcessLoop 要继续睡到 1 秒超时才会醒来。调用后立即唤醒，实现**亚秒级响应**。

### 3.4.8 broadcastTick() — 周期性广播（100ms 定时器）

```java
private void broadcastTick() {
    if (!running) return;

    try {
        if (taskActive) {
            // ── 探索完成判定（双保险） ──
            long unexploredCount = getUnexploredCount();
            double explored = getExploredPercent();
            if (unexploredCount == 0 && explored >= 99.9) {
                log.info("巡检完成！未探索格子=0, 探索率={}%", explored);
                taskActive = false;
                bb.setTaskActive(false);
                recording = false;
                wakeTaskProcessor();
            }

            // ── 兜底受阻检查 ──
            fallbackBlockedCheck();

            // ── 驱动小车 ──
            if (!bb.isGlobalPaused()) {
                tickDriveCars();
            }
            tickCount++;
            saveSnapshotIfRecording();

            if (tickCount % 20 == 0) {  // 每 20 个 tick（2 秒）打印一次状态
                log.info("节拍 #{} 完成，未探索剩余: {}, 探索率: {}%", tickCount, unexploredCount, explored);
            }
        }
        broadcastViewRefresh();  // 无论是否 taskActive 都广播（让前端看到暂停状态）
    } catch (Exception e) {
        log.error("广播节拍出错", e);
    }
}
```

**探索完成判定的双保险**：

```
条件 1: unexploredCount == 0         → unexplored:set 为空
条件 2: explored >= 99.9%            → BITCOUNT 计算探索率

两个条件都满足 → 确认探索完成
```

**为什么需要双保险？**
Redis 的 BITCOUNT 和 SCARD 是两个独立的操作。如果 Redis 崩溃重启：
- `map:view` bitmap 可能完好（因为 RDB 快照）
- `unexplored:set` 可能丢失（因为某些操作未持久化）

只依赖 `unexplored:set` 可能在 Redis 重启后误判为"完成"。双保险避免了这个问题。

```java
if (tickCount % 20 == 0) {
    log.info("节拍 #{} 完成，未探索剩余: {}, 探索率: {}%", tickCount, unexploredCount, explored);
}
```

`tickCount % 20 == 0` 表示每 20 次广播（20 × 100ms = 2 秒）打印一次日志，避免日志洪水。

### 3.4.9 tickDriveCars() — 驱动空闲小车

```java
private void tickDriveCars() {
    boolean globalPaused = bb.isGlobalPaused();
    List<String> carIds = getAllCarIds();

    for (String carId : carIds) {
        if (!isMyCar(carIds, carId)) continue;  // 不归我管
        try {
            if (bb.getCarStatus(carId) != CarStatus.IDLE) continue;  // 不是空闲状态

            // 暂停检查
            if (globalPaused) continue;
            String owner = bb.getCarOwner(carId);
            if (owner != null && !owner.isEmpty() && bb.isOperatorPaused(owner)) {
                continue;
            }

            Point next = bb.peekNextStep(carId);  // 查看路径下一步
            if (next == null) continue;  // 没有路径

            log.debug("tickDrive: carId={}, next=({},{})", carId, next.x, next.y);
            JSONObject moveData = new JSONObject();
            moveData.put("carId", carId);
            sendCommand(CommandType.MOVE_STEP, moveData, ConfigConstants.carQueueName(carId));
        } catch (Exception e) {
            log.warn("tickDrive 车辆 {} 失败", carId, e);
        }
    }
}
```

**这条方法回答了"小车怎么动起来的"**：

```
每 100ms 的 tick 中：
  遍历所有小车
    ├─ 不是我的车？跳过
    ├─ 不是 IDLE？跳过（MOVING 或 BLOCKED 不能发新命令）
    ├─ 全局/个人暂停？跳过
    ├─ 没有路径？跳过（peekNextStep == null）
    └─ 全部通过 → 发 MOVE_STEP 到 Car:{id} 队列
```

**为什么只在 IDLE 状态时才发 MOVE_STEP？**
- IDLE：车空闲，可以发新命令
- MOVING：车正在移动（处理上一个 MOVE_STEP），不能重复发
- BLOCKED：车被堵住了，需要等待超时恢复，不能发命令

**`peekNextStep()` vs `popNextStep()` 的区别**：
- `peekNextStep()`：只看不取（LRANGE -1 -1），路径不受影响
- `popNextStep()`：看并取走（RPOP），路径缩短一个点

Controller 用 `peekNextStep()` 来"检查是否有路要走"，而 Car 用 `popNextStep()` 来"走出那一步"。

### 3.4.10 handleBlockedTimeout() — 受阻超时恢复

```java
private void handleBlockedTimeout(String carId) {
    long blockedTick;
    try { blockedTick = bb.getCarBlockedTick(carId); } catch (Exception e) { blockedTick = 0; }
    long diff = tickCount - blockedTick;

    if (diff >= ConfigConstants.BLOCKED_TIMEOUT_TICKS) {  // BLOCKED_TIMEOUT_TICKS = 2
        log.info("小车 {} 已阻塞 {} 个节拍，清空路径/目标，转为 IDLE", carId, diff);
        DistributedLock lock = bb.getCarLock(carId);
        if (!lock.tryLock()) {
            log.warn("获取小车 {} 锁失败，延迟处理", carId);
            return;
        }
        try {
            bb.clearCarRoute(carId);       // 清空路径
            bb.clearCarTarget(carId);      // 清空目标
            bb.setCarStatus(carId, CarStatus.IDLE);  // 恢复 IDLE
            bb.pushTask("ROUTE_NEEDED", carId, null); // 重新请求路径
        } finally {
            lock.unlock();
        }
    }
}
```

**逐个讲解**：

```java
long blockedTick = bb.getCarBlockedTick(carId);
long diff = tickCount - blockedTick;
```

- `blockedTick`：车被堵住时 Controller 的 tick 计数
- `diff`：已经过去了多少个 tick
- `BLOCKED_TIMEOUT_TICKS = 2`：2 个 tick（200ms）后超时

```java
if (diff >= 2) {  // 被堵了 200ms 以上
```

**受阻恢复流程**：

```
tick N:    Car 发现下一步有障碍 → 设为 BLOCKED → 记录 blockedTick=N
tick N+1:  Controller 检测到 blocked, diff=1 → 还没到 2，不管
tick N+2:  Controller 检测到 blocked, diff=2 → 超时！
           ├─ 获取分布式锁（防止多个 Controller 同时处理）
           ├─ 清空路径（旧路径可能指向障碍物）
           ├─ 清空目标（原目标暂时不可达）
           ├─ 设为 IDLE
           └─ 推入 ROUTE_NEEDED → 触发重新规划
```

**为什么用分布式锁？**

在多实例 Controller 场景下，两个实例可能同时检测到同一辆车被阻塞并尝试恢复。分布式锁确保只有一个实例能成功执行恢复操作：

```
实例 0: tryLock() → 成功 → 执行恢复 → unlock()
实例 1: tryLock() → 失败（锁被 0 持有）→ return（跳过）
```

```java
} finally {
    lock.unlock();  // 无论成功还是异常，都要释放锁！
}
```

**`try-finally` 的重要性**：即使 `clearCarRoute` 等操作抛了异常，锁也一定会被释放。避免了"死锁"（锁永远不被释放）。

### 3.4.11 isMyCar() — 多实例分片

```java
private boolean isMyCar(List<String> carIds, String carId) {
    if (totalInstances <= 1) return true;  // 单实例 → 所有车都归我管
    int idx = carIds.indexOf(carId);
    return idx >= 0 && (idx % totalInstances) == instanceId;
}
```

**分片算法讲解**：

```

  索引 3 % 2 = 1 ✗ → Car004 不归我

实例 1 (instanceId=1):

  索引 1 % 2 = 1 ✓ → Car002 归我
  索引 2 % 2 = 0 ✗ → Car003 不归我
  索引 3 % 2 = 1 ✓ → Car004 归我
```

### 3.4.12 saveSnapshotIfRecording() — 快照录制

```java
private void saveSnapshotIfRecording() {
    if (!recording) return;
    try {
        JSONObject snap = new JSONObject();
        snap.put("tick", tickCount);
        snap.put("timestamp", System.currentTimeMillis());
        snap.put("mapWidth", bb.getMapWidth());
        snap.put("mapHeight", bb.getMapHeight());
        snap.put("exploredRate", getExploredPercent() / 100.0);
        snap.put("taskActive", taskActive);

        // 采集所有小车状态
        JSONArray cars = new JSONArray();
        for (String id : getAllCarIds()) {
            JSONObject cs = new JSONObject();
            cs.put("carId", id);
            cs.put("status", bb.getCarStatus(id).name());
            cs.put("position", JSON.toJSON(bb.getCarPosition(id)));
            cs.put("steps", bb.getCarSteps(id));
            cs.put("target", JSON.toJSON(bb.getCarTarget(id)));
            cs.put("owner", bb.getCarOwner(id));
            cars.add(cs);
        }
        snap.put("cars", cars);

        // 采集探索 bitmap（1600 个 '0'/'1' 字符）
        StringBuilder sb = new StringBuilder();
        boolean[][] map = bb.getMapView();
        for (int y = 0; y < bb.getMapHeight(); y++)
            for (int x = 0; x < bb.getMapWidth(); x++)
                sb.append(map[y][x] ? '1' : '0');
        snap.put("mapBits", sb.toString());

        // 采集障碍物 bitmap
        StringBuilder sb2 = new StringBuilder();
        boolean[][] blocked = bb.getMapBlocked();
        for (int y = 0; y < bb.getMapHeight(); y++)
            for (int x = 0; x < bb.getMapWidth(); x++)
                sb2.append(blocked[y][x] ? '1' : '0');
        snap.put("blockedBits", sb2.toString());

        snap.put("globalPaused", bb.isGlobalPaused());
        snap.put("completed", getUnexploredCount() == 0 && getExploredPercent() >= 99.9);

        // RPUSH 追加到快照列表尾部
        try (Jedis j = bb.getJedis()) {
            j.rpush("replay:snapshots", snap.toJSONString());
        }
    } catch (Exception e) { /* 录制失败不影响主流程 */ }
}
```

**快照内容讲解**：

每 100ms 录一帧，每帧包含：

| 字段 | 说明 |
|------|------|
| `tick` | 第几个节拍 |
| `timestamp` | 实际时间戳 |
| `exploredRate` | 探索率（0.0 ~ 1.0） |
| `cars` | 所有小车的状态/位置/步数/目标/归属 |
| `mapBits` | 1600 个字符，'1'=已探索，'0'=未探索 |
| `blockedBits` | 1600 个字符，'1'=有障碍物 |
| `globalPaused` | 是否全局暂停 |
| `completed` | 是否探索完成 |

**为什么 bitmap 用字符串而不是二进制？**
字符串在 JSON 中更容易传输和处理。前端可以直接按索引解析：`mapBits[offset] === '1'`。虽然 1600 字节比 200 字节（纯二进制 bitmap）大，但 JSON 序列化的便利性更重要。

**`try (Jedis j = bb.getJedis())` 是什么？**
这是 Java 的 **try-with-resources** 语法。`try(...)` 中的资源在代码块结束后会自动关闭。这是防止 Redis 连接泄漏的关键机制。

### 3.4.13 sendCommand() — 命令发送

```java
private void sendCommand(CommandType cmd, JSONObject data, String destination) {
    sendCommand(cmd, data, destination, false);
}

private void sendCommand(CommandType cmd, JSONObject data, String destination, boolean fanout) {
    JSONObject msg = new JSONObject();
    msg.put("cmd", cmd.name());    // 如 "NAVIGATE"
    msg.put("data", data);          // 如 {"carId":"Car001"}
    msg.put("timestamp", System.currentTimeMillis());

    try {
        if (fanout) {
            mq.fanoutPublish(destination, msg.toJSONString());  // Fanout 广播
        } else {
            mq.publish(destination, msg.toJSONString());        // 普通队列发送
        }
    } catch (Exception e) {
        log.error("发送消息失败: {} -> {}", cmd, destination, e);
    }
}
```

**两种发送模式**：

| 模式 | 方法 | 使用场景 |
|------|------|---------|
| **普通队列发送** | `mq.publish(destination, msg)` | NAVIGATE → Navigator4CarID, MOVE_STEP → Car:{id}, FORWARD_CONFIG → TaskConfigCmd |
| **Fanout 广播** | `mq.fanoutPublish(destination, msg)` | REFRESH_ALL → UpdateView（所有 Display 实例都收到） |

**消息格式**：
```json
{
  "cmd": "NAVIGATE",
  "data": {"carId": "Car001"},
  "timestamp": 1717401600000
}
```

所有模块看到这个消息后，根据 `cmd` 字段决定如何处理。

## 总结

通过本文档，你应该已经理解了：

1. **整体架构**：黑板模式（Redis 共享存储）+ C2 架构（Controller 唯一大脑）
2. **九大模块**：各自独立，通过 Redis 和 RabbitMQ 松耦合协作
3. **P3 核心职责**：
   - **TaskConfigurator**：地图初始化、障碍物生成、小车放置、增量管理、崩溃恢复
   - **Controller**：任务分发（ROUTE_NEEDED→NAVIGATE、MOVE_READY→MOVE_STEP）、100ms tick 驱动、探索完成判定、受阻超时恢复、快照录制、多实例分片
4. **关键算法**：网格分区出生点、0-1 BFS 路径规划、贪心目标选择、两步前瞻移动
5. **关键设计模式**：拉式任务队列、双层暂停控制、崩溃恢复、多实例分片
