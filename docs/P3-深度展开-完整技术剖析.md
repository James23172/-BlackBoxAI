# 第一章：P3 在整个系统中的角色再审视

## 1.1 P3 = 初始化器 + 调度器

P3 包含两个独立进程，职能互补：

```
                ┌──────────────────────────────┐
                │        TaskConfigurator       │
                │   (一次性任务，初始化环境)      │
                │                              │
                │  "建筑工人"：盖楼、画线、      │
                │   放车、写规则                  │
                └──────────────┬───────────────┘
                               │
                               │ 在 Redis 中创建的数据结构
                               ▼
                ┌──────────────────────────────┐
                │           Redis              │
                │   map:view, map:blocked,     │
                │   car:*, config:task,        │
                │   taskQueue, unexplored:set   │
                └──────────────┬───────────────┘
                               │
                               │ Controller 从这里拉取任务
                               ▼
                ┌──────────────────────────────┐
                │         Controller           │
                │   (持续运行，调度全局)         │
                │                              │
                │  "总指挥"：看任务、发命令、    │
                │   盯进度、做决策               │
                └──────────────────────────────┘
```

## 1.2 两个模块的不同运行模型

| 维度 | TaskConfigurator | Controller |
|------|-----------------|------------|
| **运行模式** | 被动：等 RabbitMQ 消息 | 主动：拉 Redis 任务 + 定时 tick |
| **生命周期** | 启动后永久监听，但不主动行动 | 启动后进入双线程循环 |
| **触发方式** | `basicConsume` 回调 | `BLPOP` 阻塞 + `scheduleAtFixedRate` |
| **重复性** | 每次收到 FORWARD_CONFIG 执行一次全量初始化 | 持续循环处理任务 |
| **状态** | 无状态（每次初始化从零开始） | 有状态（taskActive, tickCount, recording） |

# 第二章：数据模型深度解析

在深入 P3 代码之前，必须完全理解它操作的数据结构。

## 2.1 Point — 坐标的数字化表示

```java
public class Point {
    public int x;  // 横坐标，0 ~ mapWidth-1，从左到右
    public int y;  // 纵坐标，0 ~ mapHeight-1，从上到下
}
```

### 坐标与 Redis bitmap 的映射关系

```
地图 40×40 (x=0..39, y=0..39)，以 (2,1) 为例：

bitmap 偏移 = y * 40 + x = 1 * 40 + 2 = 42

    列 x:  0  1  2  3 ... 39
行 y=0:   [ 0][ 1][ 2][ 3]...[39]   ← 字节 0
行 y=1:   [40][41][42][43]...[79]   ← 字节 1
行 y=2:   [80][81][82][83]...[119]  ← 字节 2
...

Redis 存储：1 个 bit 对应 1 个格子
40×40=1600 bits = 200 bytes
```

### hashCode/equals 的重要性

```java
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Point)) return false;
    Point p = (Point) o;
    return x == p.x && y == p.y;
}

@Override
public int hashCode() {
    return Objects.hash(x, y);
}
```

**为什么重写这两个方法？**
TaskConfigurator 的禁区集合是 `Set<Point>`，Java 的 `HashSet` 依赖 `hashCode()` 存放元素、`equals()` 判重。如果不重写，两个 `new Point(10, 10)` 会被认为是不同的对象（因为它们的默认 hashCode 不同），禁区失效。

### distanceTo — 曼哈顿距离

```java
public int distanceTo(Point other) {
    return Math.abs(this.x - other.x) + Math.abs(this.y - other.y);
}
```

网格地图上不能斜走，距离 = |Δx| + |Δy|。曼哈顿距离是 BFS/A* 的基础。

## 2.2 CarStatus — 小车的三种生命状态

```java
public enum CarStatus {
    IDLE,     // 空闲，等待命令
    MOVING,   // 正在执行移动
    BLOCKED   // 被障碍物堵住，等待超时恢复
}
```

### 状态流转图

```
              [T0] 初始化
                │
                ▼
        ┌──────────────┐
        │     IDLE     │ ← 初始状态 / 路径耗尽 / 受阻恢复
        └──┬───────┬───┘
           │       │
  收到 MOVE_STEP   无路径(peekNextStep==null)
           │       │
           ▼       │
        ┌──────────┴───┐
        │    MOVING    │
        └──┬───────┬───┘
           │       │
   下一步有障碍    路径走完
           │       │
           ▼       │
        ┌──────────┐  │
        │  BLOCKED │  │
        └────┬─────┘  │
             │         │
    超时 200ms 后      │
    handleBlockedTimeout
             │         │
             └────┬────┘
                  ▼
               IDLE
```

**Controller 只向 IDLE 状态的车发 MOVE_STEP**，这是关键约束：
- MOVING 表示车正在处理上一个命令，不能重复发
- BLOCKED 表示车被堵，需等超时恢复

## 2.3 CommandType — 系统的军令类型

```java
public enum CommandType {
    NAVIGATE,        // Controller → Navigator: 帮我规划路径
    MOVE_STEP,       // Controller → Car: 走一步
    FORWARD_CONFIG,  // Controller → TaskConfigurator: 初始化/重置
    REFRESH_ALL,     // Controller → Display(Fanout): 刷新前端
    SET_CONFIG,      // Display → taskQueue → Controller: 应用配置
    RESET,           // Display → taskQueue → Controller: 重置
    TASK_COMPLETE    // 巡检完成标志（暂未启用）
}
```

**CommandType 不是 RabbitMQ 的 routing key**，它是 MQMessage JSON 中的一个字段 `cmd`。真正的 routing 是通过队列名称完成的。

# 第三章：TaskConfiguratorMain — 一行一行拆解

## 3.1 类声明与字段

```java
public class TaskConfiguratorMain {          // ①
    private static final Logger LOG = ...;    // ②
    private static final String TASK_CONFIG_QUEUE = "TaskConfigCmd"; // ③

    private BlackboardClient blackboard;      // ④
    private MessageBusClient messageBus;      // ⑤
    private final Random random = new Random(); // ⑥
```

**逐行解释：**

| 行 | 说明 |
|----|------|
| ① | `public class` — 这是一个独立的 Java 类，可以被其他类实例化。`Main` 后缀表示它包含 `main` 方法，可以独立运行 |
| ② | `private static final Logger` — SLF4J 日志对象。`static` 表示类级别共享（所有实例用同一个 Logger），`final` 表示不可变 |
| ③ | `TASK_CONFIG_QUEUE = "TaskConfigCmd"` — 硬编码队列名。为什么不用 ConfigConstants？因为这个模块类内部自己声明的常量，与 common 模块的 `QUEUE_TASK_CONFIG_CMD` 值相同但独立维护。**注意**：这里存在轻微重复——两个地方定义了同一个队列名 |
| ④ | `BlackboardClient blackboard` — 黑板客户端，连接 Redis。所有数据读写都通过它 |
| ⑤ | `MessageBusClient messageBus` — 消息总线客户端，连接 RabbitMQ。用于监听命令队列 |
| ⑥ | `Random random = new Random()` — Java 的伪随机数生成器。`final` 保证只创建一个实例（Random 是线程安全的），用于障碍物坐标随机生成 |

## 3.2 main() — 入口

```java
public static void main(String[] args) throws Exception {
    new TaskConfiguratorMain().start(args);
}
```

**为什么这么简洁？**
这是"入口归入口，逻辑归逻辑"原则。`main` 只做两件事：创建对象 + 调用启动。所有逻辑在 `start()` 中。好处：如果将来需要从另一个类启动 TaskConfigurator（比如 Launcher），可以直接 `new TaskConfiguratorMain().start(args)` 而不依赖命令行。

```java
public void start(String[] args) throws Exception {
```

### 3.3.3 声明队列与设置监听

```java
    Channel channel = messageBus.getChannel();
    channel.queueDeclare(TASK_CONFIG_QUEUE, true, false, false, null);

    LOG.info("任务配置器已启动，监听队列: {}", TASK_CONFIG_QUEUE);
```

**queueDeclare 五参数详解**：

```java
channel.queueDeclare(
    "TaskConfigCmd",  // ① queue: 队列名称
    true,             // ② durable: 持久化 → RabbitMQ 重启后队列还在
    false,            // ③ exclusive: 非独占 → 允许多个消费者
    false,            // ④ autoDelete: 不自动删除 → 即使没消费者也保留
    null              // ⑤ arguments: 无额外参数（如 TTL、死信队列等）
);
```

参数② `durable=true` 的深层含义：
- RabbitMQ 默认把队列存在内存中，重启后丢失
- `durable=true` 会把队列元数据写入磁盘
- 但消息是否持久化取决于发布时的 `deliveryMode`（见 MessageBusClient）

参数③ `exclusive=false` 的深层含义：
- `exclusive=true`：队列只属于声明它的连接，连接断开 → 队列自动删除
- `exclusive=false`：队列是共享的，不随连接销毁
- 我们的场景中，TaskConfigurator 可能重启，但队列不能被删除（Controller 还在向它发消息）

**设置消息消费回调**：

```java
    DeliverCallback deliverCallback = (consumerTag, delivery) -> {
        String message = new String(delivery.getBody(), StandardCharsets.UTF_8);
        try {
            handleForwardConfig(message);
        } catch (Exception e) {
            LOG.error("处理消息失败: {}", message, e);
        } finally {
            channel.basicAck(delivery.getEnvelope().getDeliveryTag(), false);
        }
    };

    channel.basicConsume(TASK_CONFIG_QUEUE, false, deliverCallback, consumerTag -> {});
```

这段代码建立了 RabbitMQ 的事件驱动模型：

```
RabbitMQ 有消息到达 TaskConfigCmd 队列
    │
    ▼
deliverCallback 被触发（在 RabbitMQ 的内部线程中）
    │
    ├─ delivery.getBody() → 消息体（字节数组）
    ├─ new String(..., UTF_8) → 转为 UTF-8 字符串
    ├─ handleForwardConfig(message) → 核心业务逻辑
    └─ channel.basicAck(tag, false) → 手动确认消息已处理
```

**手动确认 vs 自动确认的详细对比**：

| 方面 | 自动确认 (autoAck=true) | 手动确认 (autoAck=false) |
|------|------------------------|-------------------------|
| 确认时机 | RabbitMQ 发送后立即认为已处理 | 消费者显式调用 basicAck |
| 崩溃安全 | 消息可能丢失 | 消息重新入队，由其他消费者处理 |
| 实现复杂度 | 简单 | 需要在 finally 中确认 |
| 适用场景 | 日志、通知（丢一两条无所谓） | 配置初始化（不能丢） |

**`basicAck(tag, false)` 中的 `false`**：
- `false` = 只确认当前这条消息
- `true` = 批量确认：确认 deliveryTag ≤ 当前 tag 的所有消息

我们的场景中：消息是一条一条处理的，批量确认没有意义，还可能确认还没处理完的前序消息。

## 3.4 handleForwardConfig() — 完整逐行拆解

这是 TaskConfigurator 最核心的方法，约 120 行。我将它按功能分为 6 个区段。

### 3.4.1 消息解析与验证

```java
    MQMessage msg = JSON.parseObject(messageJson, MQMessage.class);
    String cmd = msg.getCmd();
    if (!"FORWARD_CONFIG".equals(cmd)) {
        LOG.warn("忽略非 FORWARD_CONFIG 命令: {}", cmd);
        return;
    }

    JSONObject data = JSONObject.parseObject(JSON.toJSONString(msg.getData()));
```

**第一行：JSON 反序列化**

```java
MQMessage msg = JSON.parseObject(messageJson, MQMessage.class);
```

这行代码做了：
1. fastjson2 的 `JSON.parseObject()` 接收 JSON 字符串和目标类型
2. 内部利用 Java 反射读取 `MQMessage` 类的字段名（`cmd`, `data`, `timestamp`）
3. 从 JSON 中提取同名键的值
4. 创建 `MQMessage` 对象并赋值

示例：
```
输入:  {"cmd":"FORWARD_CONFIG","data":{"mapWidth":"40"},...}
输出:  MQMessage{cmd="FORWARD_CONFIG", data={mapWidth=40}, timestamp=...}
```

**第三行：防御性检查**

```java
if (!"FORWARD_CONFIG".equals(cmd))
```

注意写法是 `"FORWARD_CONFIG".equals(cmd)` 而不是 `cmd.equals("FORWARD_CONFIG")`。为什么？因为如果 `cmd` 是 null：
- `"FORWARD_CONFIG".equals(null)` → `false`（安全）
- `null.equals("FORWARD_CONFIG")` → `NullPointerException`（崩溃）

这是一种防御性编程习惯，在 Java 中广泛使用。

**第四行：Map 转 JSONObject**

```java
JSONObject data = JSONObject.parseObject(JSON.toJSONString(msg.getData()));
```

看起来绕：`msg.getData()` 返回 `Map<String, Object>` → `JSON.toJSONString()` 转成 JSON 字符串 → `JSONObject.parseObject()` 转成 `JSONObject`。

**为什么这么绕？**
`MQMessage.data` 是 `Map<String, Object>` 类型，其中的数字可能被 JSON 库自动推断为 `Integer` 或 `Long` 或 `Double`。但 `JSONObject` 提供了 `getIntValue(String key, int defaultValue)` 和 `getBooleanValue(String key, boolean defaultValue)` 等方法，处理起来更方便。这步转换统一了数据类型处理。

### 3.4.2 增量添加小车

```java
    boolean addCar = data.getBooleanValue("addCar", false);
    if (addCar) {
        String carId = data.getString("addCarId");
        int cx = data.getIntValue("x", ConfigConstants.DEFAULT_MAP_WIDTH / 2);
        int cy = data.getIntValue("y", ConfigConstants.DEFAULT_MAP_HEIGHT / 2);
        if (carId != null && !carId.isEmpty()) {
            blackboard.addCar(carId, cx, cy);
            String machine = data.getString("machine");
            if (machine != null && !machine.isEmpty()) {
                blackboard.setCarOwner(carId, machine);
            }
            try {
                messageBus.getChannel().queueDeclare(
                    ConfigConstants.carQueueName(carId), true, false, false, null);
            } catch (IOException e) {
                LOG.error("声明 {} 队列失败", carId, e);
            }
            LOG.info("增量添加小车完成: carId={}, position=({},{})", carId, cx, cy);
        }
        return;  // ← 关键！增量操作到此结束
    }
```

**`return` 的含义**：

增量添加小车是一个独立的操作路径，与全量初始化互斥：
```
addCar=true → 执行增量添加 → return（跳过后续所有全量初始化代码）
addCar=false（默认）→ 跳过此段 → 继续向下执行
```

这是 Early Return 模式：先处理特例，特例结束后立即返回，主流程不需要嵌套在 else 中。

**`blackboard.addCar(carId, cx, cy)` 内部做了什么？**

```java
// BlackboardClient.addCar() 的完整流程

        // 1. 写入位置（Redis Hash）
        jedis.hset("car:" + carId + ":position", "x", String.valueOf(x));

        if (carsJson != null && !carsJson.isEmpty()) {
            cars = new ArrayList<>(JSON.parseArray(carsJson, String.class));
        } else {
            cars = new ArrayList<>();
        }
        if (!cars.contains(carId)) {
            cars.add(carId);
            jedis.hset("config:task", "cars", JSON.toJSONString(cars));
        }

        // 5. 点亮出生点 3×3
        illuminateArea(x, y);

        // 6. 推入 ROUTE_NEEDED 任务
        pushTask("ROUTE_NEEDED", carId, null);
    }
}
```

- 清理标记 → 那个位置恢复为可通行

### 3.4.4 崩溃恢复机制

```java
    boolean forceReset = data.getBooleanValue("forceReset", false);
    Map<String, String> existingConfig = blackboard.getTaskConfig();
    if (!forceReset && existingConfig != null && !existingConfig.isEmpty()) {
        LOG.info("检测到已有配置 (forceReset=false)，跳过全量初始化，复用现有状态");

        return;
    }
```

**崩溃恢复的完整场景分析**：

```
场景 A：正常首次启动
  Redis 是空的 → existingConfig == null → 条件不成立 → 继续执行全量初始化

场景 B：TaskConfigurator 崩溃后重启
  Redis 中有上次初始化的数据 → existingConfig != null && !isEmpty()
  → forceReset=false（默认） → 条件成立 → 跳过初始化
  → 执行 BGSAVE 持久化当前数据作为崩溃恢复快照

场景 C：用户在浏览器点击"重置"
  Controller 发 FORWARD_CONFIG(forceReset=true)
  → forceReset=true → 条件不成立 → 执行全量初始化（clearAll + 重建）

场景 D：Redis 崩溃后重启，但 TaskConfigurator 没重启
  Redis 重启后数据丢失 → existingConfig 为空
  → 但 TaskConfigurator 不知道，因为它是事件驱动的
  → 需要外部触发（如用户点"重置"或重启 TaskConfigurator）
```

**`bgsave()` 的深层含义**：

```java
try { blackboard.getJedis().bgsave(); } catch (Exception e) { /* ignore */ }
```

- `BGSAVE`：Redis 在后台 fork 子进程，将当前内存数据写入 `dump.rdb` 文件
- 主进程继续服务，不受影响
- 如果 Redis 重启，从 `dump.rdb` 恢复数据
- `/* ignore */`：持久化失败不影响主流程（程序能继续跑，只是崩溃恢复能力减弱）

**为什么崩溃恢复这么重要？**
在多机分布式部署中，TaskConfigurator 可能运行在客户机上，而 Redis 在主机上。如果 TaskConfigurator 崩溃：
- 不恢复 → 地图、小车状态全在 Redis 中完好无损 → Controller 继续调度 → 任务继续
- 恢复的关键不在于 TaskConfigurator 本身（它只是个"初始化工具"），而在于确保 Redis 数据不丢失

```java
        // 定义要清理的 key 模式
        String[] patterns = {
            "map:*",        // 地图 bitmap
            "car:*",        // 所有小车数据
            "config:*",     // 任务配置
            "lock:*",       // 分布式锁
            "unexplored:*", // 未探索索引
            "taskQueue",    // 任务队列（精确匹配）
```

```java
public void initUnexploredSet(int width, int height) {
    try (Jedis jedis = pool.getResource()) {
        String key = "unexplored:set";
        jedis.del(key);  // 先删除旧的
        String[] members = new String[width * height];  // 40×40=1600
        int idx = 0;
        for (int y = 0; y < height; y++) {
            for (int x = 0; x < width; x++) {
                members[idx++] = x + "," + y;  // "0,0", "1,0", ...
            }
        }
        // 分批 SADD（每批 1000 个），避免单次命令过大
        int batchSize = 1000;
        for (int i = 0; i < members.length; i += batchSize) {
            int end = Math.min(i + batchSize, members.length);
            jedis.sadd(key, Arrays.copyOfRange(members, i, end));
        }
    }
}
```

**分批写入的必要性**：
- Redis 单次命令传输大量参数可能导致网络超时
- 1600 个元素 × 平均 5 字节/元素 = ~8KB → 在本地网络上没问题
- 但在慢速网络或远程 Redis 上，分批写入更安全

```java
private List<Point> computeSpawnPoints(int mapWidth, int mapHeight, int carCount) {
    if (carCount <= 0) return new ArrayList<>();

    int cols = (int) Math.ceil(Math.sqrt(carCount));
    int rows = (int) Math.ceil((double) carCount / cols);
    int cellW = mapWidth / cols;
    int cellH = mapHeight / rows;
    // ...
}
```

**网格布局公式推导**：

目标是让 N 辆车尽可能均匀分布在矩形的 W×H 地图上。

```
step 1: 决定网格列数 cols = ⌈√N⌉
  - 为什么用 sqrt？因为正方形网格最均匀（行列数接近）
  - ceil 是因为要确保格数 >= 车辆数

step 2: 决定网格行数 rows = ⌈N / cols⌉
  - 确保总格数 cols × rows >= N

step 3: 每格尺寸 cellW = W / cols, cellH = H / rows

step 4: 每辆车放在对应格子的中心 (col*cellW + cellW/2, row*cellH + cellH/2)
```

**不同车数的网格布局**：

```
N=1:  cols=1, rows=1 → 1×1网格，cell=40×40 → 出生点(20,20)
N=2:  cols=2, rows=1 → 2×1网格，cell=20×40 → (10,20), (30,20)
N=3:  cols=2, rows=2 → 2×2网格，cell=20×20 → (10,10),(30,10),(10,30)
N=4:  cols=2, rows=2 → 2×2网格，cell=20×20 → (10,10),(30,10),(10,30),(30,30)
N=5:  cols=3, rows=2 → 3×2网格，cell=13×20 →
      (6,10), (19,10), (33,10), (6,30), (19,30)
N=6:  cols=3, rows=2 → 3×2网格 → (6,10),(19,10),(33,10),(6,30),(19,30),(33,30)
N=7:  cols=3, rows=3 → 3×3网格 →
      (6,6),(19,6),(33,6),(6,20),(19,20),(33,20),(6,33)
N=8:  cols=3, rows=3 → ... (8 格中的 8 个)
N=9:  cols=3, rows=3 → 完整 3×3 网格
N=16: cols=4, rows=4 → 完整 4×4 网格
```

**`buildForbiddenZone()` 的集合运算**：

```java
private Set<Point> buildForbiddenZone(List<Point> spawnPoints, int mapWidth, int mapHeight) {
    Set<Point> forbidden = new HashSet<>();
    for (Point spawn : spawnPoints) {
        for (int dy = -1; dy <= 1; dy++) {
            for (int dx = -1; dx <= 1; dx++) {
                int nx = spawn.x + dx;
                int ny = spawn.y + dy;
                if (nx >= 0 && nx < mapWidth && ny >= 0 && ny < mapHeight) {
                    forbidden.add(new Point(nx, ny));
                }
            }
        }
    }
    return forbidden;
}
```

**禁区大小计算**：
- 每个出生点产生 3×3=9 个禁区格（边界处可能少于 9）
- 4 个出生点最多产生 36 个禁区格（如果它们距离远）
- 如果出生点太近（比如 1×4 布局），禁区可能重叠，实际禁区格会少于 36
- 禁区用 `HashSet<Point>` 存储，`contains()` 操作 O(1)

```java
private int generateObstacles(int mapWidth, int mapHeight,
                               double obstacleDensity, Set<Point> forbidden) {
    int totalCells = mapWidth * mapHeight;   // 40×40=1600
    int targetObstacleCount = (int) (totalCells * obstacleDensity);  // 1600×0.1=160

    int placed = 0;
    int maxAttempts = targetObstacleCount * 20;  // 160×20=3200 次尝试
    int attempts = 0;
    List<Point> obstacles = new ArrayList<>();

    while (placed < targetObstacleCount && attempts < maxAttempts) {
        int x = random.nextInt(mapWidth);
        int y = random.nextInt(mapHeight);
        Point p = new Point(x, y);
        attempts++;

        if (!forbidden.contains(p) && !blackboard.isBlocked(x, y)) {
            obstacles.add(p);
            placed++;
        }
    }

    if (placed < targetObstacleCount) {
        LOG.warn("障碍物生成不足: 目标={}, 实际={}", targetObstacleCount, placed);
    }

    blackboard.setBlockedBatch(obstacles);
    LOG.info("已生成 {} 个障碍物 (目标: {})", placed, targetObstacleCount);
    return placed;
}
```

**为什么 maxAttempts = targetObstacleCount × 20？**

考虑最坏情况：禁区很大，随机选到的点大概率落入禁区。
```
假设禁区 36 格，地图 1600 格
每次尝试命中非禁区概率 = (1600-36)/1600 ≈ 97.75%
看起来很高，但这是"有放回抽样"（可能重复命中同一个非禁区格）

随着放置数增加（如第 150 个），已占据 150 个非禁区格
每次尝试命中可用格概率 ≈ (1600-36-150)/1600 ≈ 88.4%

160 次成功放置需要的期望尝试次数 ≈
  160 / 0.9775 + 160 / 0.9500 + ... + 160 / 0.8840
  ≈ 164 + 168 + ... + 181 ≈ 160×(1/平均概率) ≈ 160×1.1 ≈ 176 次

所以 3200 次尝试远超实际需要的 ~180 次，足够安全。
```

如果 `placed < targetObstacleCount`（达到 maxAttempts 但障碍物不够）：
- 说明地图可能太小或禁区太大，物理上放不下这么多障碍物
- 只输出警告，不抛异常
- 系统可以正常运行（只是障碍物比预期少）

**`setBlockedBatch()` 的 Pipeline 实现**：

```java
public void setBlockedBatch(List<Point> obstacles) {
    refreshMapConfig();
    try (Jedis jedis = pool.getResource()) {
        var pipeline = jedis.pipelined();  // 开启 Pipeline
        for (Point obs : obstacles) {
            pipeline.setbit("map:blocked", bitmapOffset(obs.x, obs.y), true);
            pipeline.srem("unexplored:set", obs.x + "," + obs.y);
        }
        pipeline.incr("map:blocked:version");
        pipeline.sync();  // 一次性发送所有命令
    }
    cachedMapBlockedBytes = null;
    cachedMapBlockedVersion = -1;
}
```

**Pipeline 的性能对比**：

```
不使用 Pipeline（逐条发送）：
  for (Point obs : obstacles) {
      jedis.setbit(...)         // 网络往返 0.5ms × 160 = 80ms
      jedis.srem(...)           // 网络往返 0.5ms × 160 = 80ms
  }
  总计：160ms（仅网络延迟，忽略执行时间）

使用 Pipeline（批量发送）：
  pipeline.setbit(...) × 160   // 攒在本地缓冲区
  pipeline.srem(...) × 160     // 攒在本地缓冲区
  pipeline.sync()              // 一次性发送 320 条命令 → 1 次网络往返 ≈ 0.5ms
  总计：~1ms
  
性能提升：160x
```

**为什么障碍物也要从 unexplored:set 移除？**
障碍物格子永远不能被探索（车不能通过），所以从"未探索集合"中移除，避免 TargetPlanner 把它们当作目标。否则车会被引导到一个永远无法到达的障碍物格子。

```java
public void illuminateArea(int cx, int cy) {
    refreshMapConfig();
    int r = ConfigConstants.ILLUMINATE_RADIUS;  // r=1
    try (Jedis jedis = pool.getResource()) {
        var pipeline = jedis.pipelined();
        for (int dy = -r; dy <= r; dy++) {        // dy: -1, 0, 1
            for (int dx = -r; dx <= r; dx++) {     // dx: -1, 0, 1
                int nx = cx + dx;
                int ny = cy + dy;
                if (nx >= 0 && nx < mapWidth && ny >= 0 && ny < mapHeight
                        && !isBlocked(nx, ny)) {   // ← 跳过障碍物
                    pipeline.setbit("map:view", bitmapOffset(nx, ny), true);
                    pipeline.srem("unexplored:set", nx + "," + ny);
                }
            }
        }
        pipeline.incr("map:view:version");
        pipeline.sync();
    }
    cachedMapViewBytes = null;
    cachedMapViewVersion = -1;
}
```

## 4.4 start() 方法

```java
    public void start() {
        running = true;
        // 清除上次运行残留的活跃状态
        bb.setTaskActive(false);
        bb.clearTaskQueue();

        // 启动事件驱动任务处理线程
        taskProcessor = new Thread(this::taskProcessLoop, "controller-task-processor");
        taskProcessor.setDaemon(true);
        taskProcessor.start();

        // 启动周期性广播调度器
        broadcastScheduler.scheduleAtFixedRate(this::broadcastTick,
                ConfigConstants.TICK_INTERVAL_MS, ConfigConstants.TICK_INTERVAL_MS,
                TimeUnit.MILLISECONDS);
    }
```

**清除残留状态的意义**：

场景：Controller 崩溃了（比如 OOM），Redis 中残留：
```
config:task.taskActive = "1"     ← 上次崩溃前设的
taskQueue = [ROUTE_NEEDED:Car001, ...]  ← 上次崩溃前推入的
```

新 Controller 启动：
1. `bb.setTaskActive(false)` → 重置为 inactive（保证不意外激活）
2. `bb.clearTaskQueue()` → 清空任务队列（旧任务可能指向不存在的地图）
3. 用户需要重新点"开始"才能激活任务

如果不清除：新 Controller 启动后会立刻处理旧任务，但地图可能是空的（如果 Redis 也重启过），导致不可预期的行为。

**`taskProcessor.setDaemon(true)` 的重要性**：

```java
// 守护线程 vs 用户线程
Thread daemon = new Thread(...);
daemon.setDaemon(true);   // JVM 退出时不等待这个线程

Thread user = new Thread(...);
// 默认非守护 → JVM 必须等这个线程结束才能退出
```

如果 taskProcessor 不是守护线程，当 main 线程结束后，JVM 不会退出——它会一直等待 taskProcessor（因为在 `while(running)` 循环中，除非 `running=false` 否则不会结束）。守护线程确保 Ctrl+C 时 JVM 能干净退出。

## 4.5 taskProcessLoop() — 逐行深度拆解

这是整个 Controller 的核心所在。

```java
    private void taskProcessLoop() {
        log.info("🔧 任务处理线程启动 (纯 Redis BLPOP), taskActive={}", taskActive);
        while (running) {                         // ← 只要 Controller 在运行
            try {
                // ======== 阶段 1: 等待激活 ========
                if (!taskActive) {
                    synchronized (taskWakeLock) {   // 获取 taskWakeLock 的监视器锁
                        if (!taskActive && running) { // 双重检查
                            taskWakeLock.wait(1000); // 释放锁，等待通知，最多 1 秒
                        }
                    }
```

**synchronized 块的深入讲解**：

```java
synchronized (taskWakeLock) {
    // 进入此块的条件：当前线程成功获取 taskWakeLock 对象的监视器锁
    // 同一时间只有一个线程能持有 taskWakeLock 的锁
    // 如果有其他线程也在 synchronized(taskWakeLock)，它们会阻塞等待

    if (!taskActive && running) {
        taskWakeLock.wait(1000);
        // wait() 做了三件事：
        // 1. 释放 taskWakeLock 的锁（让其他线程可以进入 synchronized 块）
        // 2. 让当前线程进入 WAITING 状态
        // 3. 被 notifyAll() 唤醒或超时后重新竞争锁
    }
}
// 离开 synchronized 块时自动释放锁
```

**为什么需要双重检查？**
```java
if (!taskActive) {                        // 第一次检查（无锁）
    synchronized (taskWakeLock) {
        if (!taskActive && running) {      // 第二次检查（有锁）
            taskWakeLock.wait(1000);
        }
    }
}
```

场景：taskActive 在第一次检查和获取锁之间被另一个线程改为 true：
```
时间线:
  T1: Thread-1 检查 taskActive → false → 准备进入 synchronized
  T2: Thread-2 wakeTaskProcessor() → 获取 taskWakeLock 锁 → notifyAll() → 释放锁
  T3: Thread-1 获取 taskWakeLock 锁 → 如果不双重检查，直接 wait() → 错过通知！
```

双重检查确保：从"第一次检查"到"wait()"的窗口期被锁保护，不会遗漏通知。

**`wait(1000)` vs `wait()` vs `sleep(1000)`**：

| 操作 | 锁行为 | 唤醒方式 |
|------|--------|---------|
| `wait(1000)` | **释放锁**，超时后重新竞争 | notifyAll() 或超时 |
| `wait()` | **释放锁**，无限等待 | 只能 notifyAll() |
| `sleep(1000)` | **不释放锁** | 超时 |

我们的选择 `wait(1000)`：
- 释放锁（关键！否则 wakeTaskProcessor() 无法进入 synchronized 块）
- 超时（关键！每 1 秒醒来检查 Redis 中的 taskActive）

```java
                    // 超时唤醒后检查 Redis 中的 taskActive
                    if (!taskActive && running) {
                        try {
                            boolean redisActive = bb.isTaskActive();
                            if (redisActive) {
                                log.info("🔓 检测到 Redis taskActive=true, 激活任务处理器");
                                taskActive = true;
                            }
                        } catch (Exception e) { /* ignore, will retry next cycle */ }
                    }
                    continue;   // ← 回到 while(running) 循环开头
                }
```

**为什么超时唤醒后还要检查 Redis？**

因为 taskActive 可能不是通过 `wakeTaskProcessor()` 设置的，而是通过 Display 直接写 Redis 的：

```
场景：用户从浏览器点击"开始"
  Display → bb.setTaskActive(true)  ← 直接写 Redis
  （Display 没有调用 Controller.wakeTaskProcessor()，因为不同进程！）

Controller 如何感知？
  → taskProcessLoop 每 1 秒超时唤醒
  → 检查 Redis isTaskActive()
  → 发现 true → 设置本地 taskActive = true
```

这就是"拉式 + 轮询"的混合模型。

**`blockingPopTask(2)` 的实现**：

```java
public Map<String, String> blockingPopTask(int timeoutSeconds) {
    try (Jedis jedis = pool.getResource()) {
        List<String> result = jedis.blpop(timeoutSeconds, "taskQueue");
        // BLPOP 返回 [key, value] 数组
        // 如果超时返回 null
        if (result == null || result.size() < 2)
            return null;
        return JSON.parseObject(result.get(1), Map.class);
    }
}
```

**BLPOP 的阻塞语义**：
```
Redis BLPOP taskQueue 2

情况 1: taskQueue 非空
  → 立即弹出队首元素并返回 → 类似 LPOP，但返回 [key, value]

情况 2: taskQueue 为空
  → 客户端阻塞等待，直到有新元素被 RPUSH，或超时（2 秒）
  → 超时返回 null

情况 3: BLPOP 期间 taskQueue 有元素 RPUSH 进来
  → 立即返回（不等超时）
```

**连续清空的意义**：

```java
Map<String, String> next;
while ((next = bb.popTask()) != null) {  // 非阻塞 LPOP
    processTask(next);
}
```

为什么在 `blockingPopTask` 之后还要 `popTask` 循环？
- BLPOP 返回后，处理这个任务的过程中可能有新任务被 RPUSH 进来
- Navigator 可能在处理 ROUTE_NEEDED 的同时推入了 MOVE_READY
- 如果不连续清空，MOVE_READY 要等到下一轮 BLPOP（最多 2 秒后）才被处理
- 连续清空确保延迟最小化

**异常处理的三种情况**：

```java
catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // ① 恢复中断标志
    break;                                // ② 退出循环
}
```

`InterruptedException` 在以下情况抛出：
- `taskWakeLock.wait(1000)` 被 `Thread.interrupt()` 中断
- `Thread.sleep(500)` 被中断

正确处理方式：`Thread.currentThread().interrupt()` 恢复中断标志，然后 `break` 退出循环。不要"吞掉"中断。

```java
catch (Exception e) {
    log.error("任务处理异常", e);
    try { Thread.sleep(500); }             // ③ 冷却 500ms
    catch (InterruptedException ie) {
        Thread.currentThread().interrupt();
        break;
    }
}
```

如果 Redis 暂时不可用（比如 Redis 重启中）：
- BLPOP 会抛异常
- 我们 `sleep(500)` 后重试（循环回到开头）
- 这样可以自动从 Redis 断连中恢复

## 4.6 processTask() — 任务分发中心

```java
    private void processTask(Map<String, String> task) {
        String type = task.get("type");
        String carId = task.get("carId");

        // ── 全局任务（无 carId）──
        switch (type) {
            case "START":        handleStartTask();     return;
            case "PAUSE":        handlePauseTask();     return;
            case "SET_CONFIG":   handleSetConfigTask(task);  return;
            case "RESET":        handleResetTask(task);      return;
            case "RECORD_START": recording = true;           return;
            case "RECORD_STOP":  recording = false;          return;
        }

        // ── 车辆相关任务 ──
        if (carId == null) {
            log.warn("taskQueue 任务缺少 carId: {}", task);
            return;
        }

        // ── 多实例分片：只处理我的车 ──
        if (!isMyCar(getAllCarIds(), carId)) return;

        switch (type) {
            case "ROUTE_NEEDED":
                requestNavigate(carId);
                break;
            case "MOVE_READY":
                // 双层暂停检查
                if (bb.isGlobalPaused()) break;
                String owner = bb.getCarOwner(carId);
                if (owner != null && !owner.isEmpty() && bb.isOperatorPaused(owner)) break;
                JSONObject moveData = new JSONObject();
                moveData.put("carId", carId);
                sendCommand(CommandType.MOVE_STEP, moveData, ConfigConstants.carQueueName(carId));
                break;
            case "ADD_CAR":
                requestNavigate(carId);
                break;
            case "BLOCKED":
                handleBlockedTimeout(carId);
                break;
            default:
                log.warn("taskQueue 未知任务类型: {}", type);
        }
    }
```

### 双层暂停检查的详细展开

```java
case "MOVE_READY":
    if (bb.isGlobalPaused()) break;              // 第 1 层
    String owner = bb.getCarOwner(carId);
    if (owner != null && !owner.isEmpty() && bb.isOperatorPaused(owner)) break;  // 第 2 层
    // 发 MOVE_STEP
```

**两层暂停的实现方式截然不同**：

**第 1 层：全局暂停**
```
Display/CommandReceiver:
  配置员点"全局暂停"
  → bb.setGlobalPause(true);
  → jedis.set("pause:global", "true")

Controller:
  processTask(MOVE_READY)
  → bb.isGlobalPaused()
  → jedis.exists("pause:global")  // O(1)
  → true → break（不发 MOVE_STEP）
```

**第 2 层：个人暂停**
```
Display/CommandReceiver:
  运行员点"我的小车暂停"
  → bb.setOperatorPause("B", true);
  → jedis.set("pause:operator:B", "true")

Controller:
  processTask(MOVE_READY)
  → String owner = bb.getCarOwner(carId)  // "B"
  → bb.isOperatorPaused("B")
```

## 4.7 handleStartTask() 的两个分支

```java
    private void handleStartTask() {
        Map<String, String> existingConfig = bb.getTaskConfig();
        boolean hasConfig = existingConfig != null && !existingConfig.isEmpty();

        if (!hasConfig) {
            // 分支 A：配置不存在 → 触发完整初始化
            userActivated = true;
            JSONObject initData = new JSONObject();
            initData.put("mapWidth", bb.getMapWidth());
            initData.put("mapHeight", bb.getMapHeight());
            initData.put("carCount", Math.max(4, bb.getAllCarIds().size()));
            initData.put("obstacleDensity", ConfigConstants.DEFAULT_OBSTACLE_DENSITY);
            initData.put("routeAlgorithm", bb.getRouteAlgorithm());
            initData.put("active", true);   // ← 初始化后直接激活
            taskActive = false;             // ← 先暂停自己
            sendCommand(CommandType.FORWARD_CONFIG, initData,
                        ConfigConstants.QUEUE_TASK_CONFIG_CMD);
        } else {
            // 分支 B：配置已存在 → 直接激活
            userActivated = true;
            bb.setTaskActive(true);
            taskActive = true;
            wakeTaskProcessor();
        }
        recording = true;
    }
```

**分支 A 的决策链路**：

```
用户点"开始"（没先点"应用配置"）
  │
  ├─ Controller 检查 config:task → 空
  ├─ 推断：用户想用默认配置开始
  ├─ 发送 FORWARD_CONFIG(active=true) 给 TaskConfigurator
  │
  └─ TaskConfigurator 处理：
       ├─ clearAll()
       ├─ 初始化地图（默认 40×40）
       ├─ 初始化 4 辆车
       ├─ 写入 config:task（taskActive=1）
       ├─ 推入 4 个 ROUTE_NEEDED
       │
       └─ Controller 继续：
            taskActive=false（在此期间 TaskConfigurator 处理）
            → TaskConfigurator 写入 taskActive=1
            → taskProcessLoop 超时唤醒 → 检查 Redis → 发现 taskActive=true
            → 开始处理 taskQueue 中的 ROUTE_NEEDED
```

**分支 B 的决策链路**：

```
用户先点"应用配置" → 再点"开始"
  │
  ├─ Controller 检查 config:task → 不为空（TaskConfigurator 已初始化好）
  ├─ bb.setTaskActive(true)
  ├─ taskActive = true
  ├─ wakeTaskProcessor() → 立即唤醒
  │
  └─ taskProcessLoop 被唤醒 → 开始处理 taskQueue 中的 ROUTE_NEEDED
```

## 4.8 handleSetConfigTask() vs handleResetTask()

```java
    private void handleSetConfigTask(Map<String, String> task) {
        JSONObject data = new JSONObject();
        // ... 解析参数 ...
        data.put("active", false);  // SET_CONFIG 不激活
        taskActive = false;
        bb.clearTaskQueue();
        sendCommand(CommandType.FORWARD_CONFIG, data, ConfigConstants.QUEUE_TASK_CONFIG_CMD);
    }

    private void handleResetTask(Map<String, String> task) {
        JSONObject data = new JSONObject();
        // ... 解析参数 ...
        data.put("reset", true);
        data.put("forceReset", true);  // 强制清除
        data.put("active", false);
        userActivated = false;
        taskActive = false;
        recording = false;
        // 清除回放快照
        try { try (Jedis j = bb.getJedis()) { j.del("replay:snapshots"); } }
        catch (Exception e) { /* ignore */ }
        tickCount = 0;
        bb.clearTaskQueue();
        sendCommand(CommandType.FORWARD_CONFIG, data, ConfigConstants.QUEUE_TASK_CONFIG_CMD);
    }
```

**差异对比表**：

| 操作 | SET_CONFIG | RESET |
|------|-----------|-------|
| **forceReset** | false | **true** |
| **对 Redis 的影响** | TaskConfigurator 检测到 existingConfig → **跳过初始化** | TaskConfigurator 检测到 forceReset=true → **force clearAll + 重建** |
| **对录制的影响** | 不停止录制 | **停止录制 + 删除快照** |
| **对 tickCount** | 不重置 | **重置为 0** |
| **对 userActivated** | 不改变 | **设为 false** |
| **触发时机** | 用户修改地图参数后点"应用配置" | 用户点"重置"按钮 |

**为什么 SET_CONFIG 不重建地图？**
因为用户只是想换个参数（比如改障碍物密度），而不是要清空现有探索进度。但如果参数改了而地图没重建，会出现数据不一致（比如 map:view bitmap 是 40×40 但 config:task 说 mapWidth=50）。

在当前实现中，这个问题被"崩溃恢复"机制部分掩盖了：
- SET_CONFIG 发 FORWARD_CONFIG(forceReset=false)
- TaskConfigurator 检测到 existingConfig → 跳过初始化
- 这意味着**SET_CONFIG 实际上不会改变任何地图参数**

这是当前实现的一个限制。完整的实现应该支持"在不重置探索进度的情况下调整地图"。

## 4.9 broadcastTick() — 100ms 周期调度

```java
    private void broadcastTick() {
        if (!running) return;

        try {
            if (taskActive) {
                // ── 探索完成判定 ──
                long unexploredCount = getUnexploredCount();
                double explored = getExploredPercent();
                if (unexploredCount == 0 && explored >= 99.9) {
                    log.info("🏁 巡检完成！未探索格子=0, 探索率={}%", explored);
                    taskActive = false;
                    bb.setTaskActive(false);
                    recording = false;
                    wakeTaskProcessor();
                }

                fallbackBlockedCheck();

                if (!bb.isGlobalPaused()) {
                    tickDriveCars();
                }
                tickCount++;
                saveSnapshotIfRecording();

                if (tickCount % 20 == 0) {
                    log.info("节拍 #{} 完成，未探索剩余: {}, 探索率: {}%",
                             tickCount, unexploredCount, explored);
                }
            }
            broadcastViewRefresh();
        } catch (Exception e) {
            log.error("广播节拍出错", e);
        }
    }
```

**探索完成判定的双保险**：

```java
if (unexploredCount == 0 && explored >= 99.9)
```

两个条件必须同时满足：

| 条件 | 数据来源 | 含义 | 失败场景 |
|------|---------|------|---------|
| `unexploredCount == 0` | `SCARD unexplored:set` | 未探索集合为空 | Redis 重启后 Set 丢失 → 误判为 0 |
| `explored >= 99.9` | `BITCOUNT map:view` | Bitmap 中 1-bit 占比 ≥ 99.9% | 障碍物被误标为已探索 → 可能超过 100% |

为什么不是 `explored >= 100.0`？
- 因为有 10% 障碍物，最大探索率 = (总格数 - 障碍物) / 总格数 ≈ 90%
- 但 `getExploredPercent()` 已经排除了障碍物（分子 = BITCOUNT, 分母 = 总格数 - 障碍物）
- 所以理论最大是 100.0%
- 使用 99.9% 是因为浮点精度误差（BITCOUNT 可能比实际探索数多 1-2 个）

**`taskActive = false` 后的连锁反应**：

```
broadcastTick 发现探索完成
  → taskActive = false
  → bb.setTaskActive(false)     → Redis 写入
  → recording = false            → 停止录制
  → wakeTaskProcessor()         → 唤醒 taskProcessLoop

taskProcessLoop 醒来:
  → 检查 taskActive → false
  → 进入等待阶段（wait(1000) 循环）
  → 不再处理新任务

broadcastTick 继续每 100ms 执行:
  → taskActive = false → 跳过探索判定、fallbackBlockedCheck、tickDriveCars
  → 但仍调用 broadcastViewRefresh() → 前端能看到"已完成"状态
```

## 4.10 tickDriveCars() — 驱动空闲小车

```java
    private void tickDriveCars() {
        boolean globalPaused = bb.isGlobalPaused();
        List<String> carIds = getAllCarIds();

        for (String carId : carIds) {
            if (!isMyCar(carIds, carId)) continue;
            try {
                if (bb.getCarStatus(carId) != CarStatus.IDLE) continue;
                if (globalPaused) continue;
                String owner = bb.getCarOwner(carId);
                if (owner != null && !owner.isEmpty() && bb.isOperatorPaused(owner)) continue;

                Point next = bb.peekNextStep(carId);
                if (next == null) continue;

                JSONObject moveData = new JSONObject();
                moveData.put("carId", carId);
                sendCommand(CommandType.MOVE_STEP, moveData, ConfigConstants.carQueueName(carId));
            } catch (Exception e) {
                log.warn("tickDrive 车辆 {} 失败", carId, e);
            }
        }
    }
```

**这也是"推动小车前进"的一个入口**。与 `processTask(MOVE_READY)` 的区别：

| 触发方式 | processTask(MOVE_READY) | tickDriveCars() |
|---------|------------------------|-----------------|
| **触发时机** | Navigator 推 MOVE_READY 进 taskQueue → Controller 拉取 | 每 100ms 自动 |
| **作用** | 首次移动（新路径就绪后的第一步） | 后续移动（IDLE 且有剩余路径） |
| **车辆状态** | 路径刚规划完，车是 IDLE | 上一步走完后设为 IDLE，有剩余路径 |

**为什么需要两个入口？**
- MOVE_READY：事件驱动，保证新路径就绪后立即开始移动（不等 tick）
- tickDriveCars：定时驱动，保证上一步走完后立即走下一步（不等下一个 MOVE_READY）

两个入口互不冲突：MOVE_READY 处理第一步，tickDriveCars 处理后续步骤。

## 4.11 handleBlockedTimeout() — 受阻超时恢复

```java
    private void handleBlockedTimeout(String carId) {
        long blockedTick;
        try { blockedTick = bb.getCarBlockedTick(carId); }
        catch (Exception e) { blockedTick = 0; }

        long diff = tickCount - blockedTick;
        if (diff >= ConfigConstants.BLOCKED_TIMEOUT_TICKS) {  // BLOCKED_TIMEOUT_TICKS = 2
            DistributedLock lock = bb.getCarLock(carId);
            if (!lock.tryLock()) {
                log.warn("获取小车 {} 锁失败，延迟处理", carId);
                return;
            }
            try {
                bb.clearCarRoute(carId);
                bb.clearCarTarget(carId);
                bb.setCarStatus(carId, CarStatus.IDLE);
                bb.pushTask("ROUTE_NEEDED", carId, null);
            } finally {
                lock.unlock();
            }
        }
    }
```

**受阻恢复的完整时间线**：

```
tick=100: Car001 发现下一步是障碍物
  → CarAgent 设 status=BLOCKED, bb.setBlockedTick("Car001", 100)
  → 推 BLOCKED 任务 → taskQueue

tick=100: Controller processTask(BLOCKED, Car001)
  → handleBlockedTimeout("Car001")
  → blockedTick=100, diff=100-100=0
  → 0 < 2 → 不处理

tick=100: fallbackBlockedCheck() 也检查到 Car001 BLOCKED
  → handleBlockedTimeout("Car001")
  → diff=0 < 2 → 不处理

tick=101: broadcastTick
  → fallbackBlockedCheck()
  → diff=101-100=1 < 2 → 不处理

tick=102: broadcastTick
  → fallbackBlockedCheck()
  → diff=102-100=2 >= 2 → 触发恢复！
  → tryLock() → 成功
  → clearCarRoute → clearCarTarget → setStatus(IDLE) → pushTask(ROUTE_NEEDED)
  → unlock()
```

**为什么 BLOCKED_TIMEOUT_TICKS = 2（即 200ms）？**
- 如果设为 0：车一被堵就清路径 → 可能只是暂时被其他车挡住，急着清路径反而浪费了已规划的路径
- 如果设太大（比如 20 tick = 2 秒）：被堵的车白白等待 2 秒，降低整体效率
- 2 tick = 200ms：给障碍物留一点"观察窗口"，但不会等太久

## 4.12 isMyCar() — 多实例分片

```java
    private boolean isMyCar(List<String> carIds, String carId) {
        if (totalInstances <= 1) return true;
        int idx = carIds.indexOf(carId);
        return idx >= 0 && (idx % totalInstances) == instanceId;
    }
```

**分片算法可视化**：

```
totalInstances=2

carIds = ["Car001", "Car002", "Car003", "Car004"]
索引:         0         1         2         3

实例 0 (instanceId=0):
  索引 0: 0 % 2 = 0 ✓ → Car001 归我
  索引 1: 1 % 2 = 1 ✗ → Car002 不归我
  索引 2: 2 % 2 = 0 ✓ → Car003 归我
  索引 3: 3 % 2 = 1 ✗ → Car004 不归我

实例 1 (instanceId=1):
  索引 0: 0 % 2 = 0 ✗ → Car001 不归我
  索引 1: 1 % 2 = 1 ✓ → Car002 归我
  索引 2: 2 % 2 = 0 ✗ → Car003 不归我
  索引 3: 3 % 2 = 1 ✓ → Car004 归我
```

**多实例的并发安全**：

两个 Controller 实例同时读写 Redis，通过以下机制保证安全：
1. **分片**：每辆车只被一个实例处理（不会有两个实例同时给同一辆车发 MOVE_STEP）
2. **分布式锁**：受阻恢复时 `getCarLock(carId).tryLock()` 确保只有一个实例执行恢复
3. **Redis 原子性**：所有 Redis 操作（SETBIT, HSET, LPOP 等）都是原子的
4. **广播独占**：只有 `instanceId=0` 广播 REFRESH_ALL，避免重复

**Fanout 广播的路径**：

```
Controller(instanceId=0) → RabbitMQ UpdateView Exchange(Fanout)
  │
  ├─ → Display(主机) 的临时队列 → StateBroadcaster → WebSocket → 主机浏览器
  ├─ → Display(客户机B) 的临时队列 → StateBroadcaster → WebSocket → 客户机B浏览器
```

**Fanout Exchange 的工作原理**：
- Fanout Exchange 忽略 routing key
- 直接把消息复制到所有绑定的队列
- 每个 Display 实例启动时创建一个临时独占队列并绑定到 UpdateView Exchange
- 所有 Display 实例几乎同时收到 REFRESH_ALL 消息（毫秒级同步）

## 4.14 saveSnapshotIfRecording() — 快照录制

```java
    private void saveSnapshotIfRecording() {
        if (!recording) return;
        try {
            JSONObject snap = new JSONObject();
            snap.put("tick", tickCount);
            snap.put("timestamp", System.currentTimeMillis());
            snap.put("mapWidth", bb.getMapWidth());
            snap.put("mapHeight", bb.getMapHeight());
            snap.put("exploredRate", getExploredPercent() / 100.0);
            snap.put("taskActive", taskActive);

            // 采集所有小车状态
            JSONArray cars = new JSONArray();
            for (String id : getAllCarIds()) {
                JSONObject cs = new JSONObject();
                cs.put("carId", id);
                cs.put("status", bb.getCarStatus(id).name());
                Point p = bb.getCarPosition(id);
                cs.put("position", p != null ? JSON.toJSON(p) : null);
                cs.put("steps", bb.getCarSteps(id));
                Point t = bb.getCarTarget(id);
                cs.put("target", t != null ? JSON.toJSON(t) : null);
                cs.put("owner", bb.getCarOwner(id));
                cars.add(cs);
            }
            snap.put("cars", cars);

            // 采集探索 bitmap（1600 个 '0'/'1' 字符）
            StringBuilder sb = new StringBuilder();
            boolean[][] map = bb.getMapView();
            for (int y = 0; y < bb.getMapHeight(); y++)
                for (int x = 0; x < bb.getMapWidth(); x++)
                    sb.append(map[y][x] ? '1' : '0');
            snap.put("mapBits", sb.toString());

            // 采集障碍物 bitmap
            StringBuilder sb2 = new StringBuilder();
            boolean[][] blocked = bb.getMapBlocked();
            for (int y = 0; y < bb.getMapHeight(); y++)
                for (int x = 0; x < bb.getMapWidth(); x++)
                    sb2.append(blocked[y][x] ? '1' : '0');
            snap.put("blockedBits", sb2.toString());

            snap.put("globalPaused", bb.isGlobalPaused());
            snap.put("completed", getUnexploredCount() == 0 && getExploredPercent() >= 99.9);

            try (Jedis j = bb.getJedis()) {
                j.rpush("replay:snapshots", snap.toJSONString());
            }
        } catch (Exception e) { /* 录制失败不影响主流程 */ }
    }
```

**快照大小估算**：

```
每帧快照 JSON 大约：
  - tick, timestamp, mapWidth, mapHeight, exploredRate, taskActive ≈ 100 字节
  - cars: 4 辆车 × (carId + status + position + steps + target + owner) ≈ 4 × 120 ≈ 480 字节
  - mapBits: 1600 字符 ≈ 1600 字节
  - blockedBits: 1600 字符 ≈ 1600 字节
  - globalPaused, completed ≈ 40 字节
  总计 ≈ 3820 字节/帧

录制 100 秒 = 1000 tick × 3820 字节 ≈ 3.8 MB
存储在 Redis List 中（rpush），全部在内存中。
```

**为什么用字符串 bitmap 而不是二进制？**
字符串 bitmap 在 JSON 中更友好：
- 前端可以直接 `mapBits[offset] === '1'` 
- 不需要二进制解码
- 虽然大了 8 倍（1600 字节 vs 200 字节），但总帧数有限（几千帧），可接受

| `getMapWidth()/getMapHeight()` | 地图尺寸 | 本地缓存（refreshMapConfig） |
| `getMapView()` | 探索 bitmap | `GET` + 版本号缓存 |
| `getMapBlocked()` | 障碍物 bitmap | `GET` + 版本号缓存 |
| `getRouteAlgorithm()` | 路径算法名 | `HGET` |
| `getExploredCount()` | 已探索计数 | `BITCOUNT` |
| `getJedis()` | 获取底层连接 | 返回 `Jedis` 对象 |

# 第六章：并发模型与线程安全分析

## 6.1 Controller 的线程模型

```
Controller 进程
  │
  ├─ main 线程
  │   └─ controller.start() → 启动后空闲（等待 JVM 退出）
  │
  ├─ taskProcessor 线程（Daemon）
  │   └─ taskProcessLoop()
  │       ├─ wait(1000) 等待激活
  │       └─ BLPOP → processTask → 连续 LPOP
  │
  ├─ broadcastScheduler 线程（ScheduledExecutorService）
  │   └─ broadcastTick() 每 100ms 执行
  │       ├─ 探索完成判定
  │       ├─ fallbackBlockedCheck()
  │       ├─ tickDriveCars()
  │       ├─ saveSnapshotIfRecording()
  │       └─ broadcastViewRefresh()
  │
  └─ ShutdownHook 线程（关闭时）
      └─ controller.stop()
```

**两个核心线程的交互**：

| 变量 | taskProcessor 线程 | broadcastScheduler 线程 | 冲突？ |
|------|-------------------|------------------------|--------|
| `taskActive` | 读 + 写（handleStartTask/PauseTask） | 读（探索完成判定） | 都用 volatile，安全 |
| `running` | 读 | 读 | 都用 volatile，安全 |
| `taskWakeLock` | wait/notify | 不涉及 | 无冲突 |
| `tickCount` | 不涉及 | 写 | 单线程度，安全 |
| `recording` | 不涉及 | 读 | volatile，安全 |

**关键：taskProcessor 和 broadcastScheduler 不会同时修改同一辆车**

- taskProcessor 通过 `processTask(MOVE_READY)` 发 MOVE_STEP
- broadcastScheduler 通过 `tickDriveCars()` 也发 MOVE_STEP

但两者有天然屏障：
- processTask 发 MOVE_STEP 后，车变为 MOVING 状态
- tickDriveCars 跳过 MOVING 状态的车（`if (status != IDLE) continue`）

## 6.2 TaskConfigurator 的线程模型

```
TaskConfigurator 进程
  │
  ├─ main 线程
  │   └─ start() → 声明队列 + basicConsume → 阻塞在 RabbitMQ 事件循环
  │
  └─ RabbitMQ 内部线程（deliverCallback）
      └─ handleForwardConfig()
          ├─ 增量添加小车（addCar/removeCar）
          └─ 全量初始化（clearAll + 重建）
```

TaskConfigurator 是单线程事件模型（RabbitMQ 保证同一 Channel 的回调串行化），没有并发问题。

# 第七章：错误处理与容错设计

## 7.1 错误处理模式总结

| 模式 | 代码示例 | 场景 |
|------|---------|------|
| **吞掉异常** | `catch (Exception e) { /* ignore */ }` | bgsave 失败、replay:snapshots DEL 失败 |
| **记录 + 继续** | `catch (Exception e) { log.error(...); }` | processTask 处理单个任务失败 |
| **冷却 + 重试** | `catch (Exception e) { sleep(500); }` | taskProcessLoop Redis 断连 |
| **中断退出** | `catch (InterruptedException e) { interrupt(); break; }` | 正常关闭 |
| **启动失败** | `catch (Exception e) { System.exit(1); }` | Redis/RabbitMQ 连不上 |

## 7.2 容错场景分析

**场景 1：Redis 暂时不可用**
```
taskProcessLoop:
  BLPOP 抛异常（连接断开）
  → catch (Exception e) → sleep(500) → while(running) 重新循环
  → 尝试 BLPOP → 如果 Redis 恢复了 → 正常
  → 如果还是不可用 → 继续 sleep(500) → 重试
```

**场景 2：RabbitMQ 暂时不可用**
```
tickDriveCars:
  sendCommand → mq.publish() → 抛异常
  → catch (Exception e) → log.warn(...)
  → 这次 MOVE_STEP 丢失了 → 但车还是 IDLE
  → 下一个 100ms tick 会重试 tickDriveCars → 再次发送
```

**场景 3：Controller 进程崩溃**
```
Controller 崩溃
  → Redis 中残留 taskActive=true, taskQueue 可能非空
  → 新 Controller 启动:
      setTaskActive(false) → 清除残留状态
      clearTaskQueue() → 清空任务队列
  → 需要用户重新点"开始"
```

## 8.2 小车状态 + 任务类型联合状态机

```
┌── IDLE ──────────────────────────────────────────┐
│                                                   │
│  1. Controller 拉取 ROUTE_NEEDED                  │
│     → requestNavigate(carId)                      │

│     → MOVE_STEP → Car:carId                       │

│                                                   │

│                                                   │

│      → Car 推 ROUTE_NEEDED                        │

│      → 回到步骤 1                                  │
│                                                   │
│  4b. 移动成功 + 路径还有剩余                       │
│      → 车变为 IDLE（但路径非空）                    │
│      → tickDriveCars 发下一步 MOVE_STEP           │
│      → 回到步骤 4                                  │
│                                                   │
│  4c. 下一步有障碍物                                │
│      → 车变为 BLOCKED                              │
│      → Car 推 BLOCKED → Controller               │
│                                                   │
├── BLOCKED ───────────────────────────────────────┤
│                                                   │
│  5. Controller handleBlockedTimeout               │
│     → diff >= 2 tick → 超时                       │
│     → 分布式锁                                     │
│     → clearCarRoute + clearCarTarget              │
│     → 车变为 IDLE                                  │
│     → pushTask(ROUTE_NEEDED)                      │
│     → 回到步骤 1                                  │
│                                                   │
└───────────────────────────────────────────────────┘
```

# 第九章：性能关键路径分析

## 9.1 关键路径延迟

| 操作 | 典型延迟 | 瓶颈 |
|------|---------|------|
| Controller BLPOP 拉任务 | 0.1-1 ms（非空）/ 2s（空） | Redis 网络 |
| processTask 分发 | < 0.1 ms | 本地逻辑 |
| sendCommand 发 NAVIGATE | 0.5-2 ms | RabbitMQ 网络 |
| Navigator BFS 规划 | 1-5 ms | CPU（1600 格 BFS） |
| Car MOVE_STEP 处理 | 0.5-1 ms | Redis Pipeline（3×3 点亮）|
| broadcastTick 一次 | 1-5 ms | BITCOUNT + SCARD + 多车状态 |
| saveSnapshot 一次 | 2-5 ms | JSON 序列化 + Redis RPUSH |

**从"路径就绪"到"车开始移动"的端到端延迟**：

```
Navigator pushRoute → pushTask(MOVE_READY)
  → Controller BLPOP 拉取 → 0-2s（取决于 BLPOP 超时）
  → processTask → sendCommand(MOVE_STEP)
  → RabbitMQ 传输 → 0.5-2ms
  → Car 处理 → 1-2ms

总延迟：0.5ms ~ 2005ms（取决于 BLPOP 是否在等待中）
```

连续清空（`while ((next = popTask()) != null)`）可大幅减少这个延迟。

## 9.2 tick 周期的负载分析

每 100ms 的 tick 需要完成：
```
1. BITCOUNT map:view          → O(N) in Redis, ~0.5ms for 1600 bits
2. SCARD unexplored:set        → O(1), ~0.1ms
3. fallbackBlockedCheck:       → 遍历 4 辆车，每辆 ~0.2ms
4. tickDriveCars:              → 遍历 4 辆车，可能发 MOVE_STEP
5. saveSnapshotIfRecording:    → 2-5ms（JSON 序列化 + RPUSH）
6. broadcastViewRefresh:       → 1-2ms（RabbitMQ Fanout）
总计：~5-10ms
```

**CPU 占用率**：5-10ms / 100ms = 5-10%，非常低。
