# 一、架构设计类

## Q1：为什么选择 C2 + 黑板模式，而不是纯事件驱动架构？

**考点**：理解架构选型的 trade-off

**回答**：

如果采用纯事件驱动（RabbitMQ 订阅模式），Controller 需要**同时订阅多个队列**：

```
Navigator4CarID  → 收到 NAVIGATE 响应 → 推 MOVE_READY
Car:Car001       → 收到 BLOCKED 响应 → 处理阻塞
...
```

**问题**：
1. **过载风险**：消息不断涌入，Controller 来不及处理就会在 RabbitMQ 中积压。但 RabbitMQ 不提供"处理速率控制"。
2. **顺序问题**：如果多条消息同时到达，处理顺序不可控。而调度器天然需要有序处理（先规划路径 → 再发移动）。
3. **测试困难**：事件驱动架构的调试比拉式架构复杂得多。

**C2 + 黑板模式的优势**：

```
Controller 通过 BLPOP 从 Redis taskQueue 拉取
→ 自己控制处理速度
→ 消息有序（FIFO）
→ 一条处理完再拉下一条
→ 即使积压，也是可控的 Redis List 积压，不影响其他模块
```

**类比如下**：

| 模式 | 类比 | 问题 |
|------|------|------|
| 事件驱动 | 老板不停给你塞任务 | 你没法控制节奏，可能过载 |
| C2 + 黑板 | 你从任务箱自己取任务 | 处理完一个再取下一个 |

**追问**："那为什么不让 Controller 也订阅 RabbitMQ 队列，但用 basicQos(1) 限流？"

`basicQos(1)` 只能限制 RabbitMQ 发给一个消费者的速率。但如果 Controller 处理慢，消息会积压在队列中。而 Redis taskQueue 的积压是可控的——可以用 `LLEN taskQueue` 监控积压量，甚至可以根据积压量动态调整处理策略。

## Q2：Controller 不订阅任何 RabbitMQ 队列，那它怎么知道 Navigator 完成了路径规划？

**考点**：理解拉式模型的闭环

**回答**：

Controller 和 Navigator 之间的交互是**异步的**，但不是通过 RabbitMQ 回调：

```
Controller                          Navigator
    │                                   │
    │── NAVIGATE(carId) ─────────────→ │ (RabbitMQ)
    │                                   │
    │   等待...                          │ 1. 找目标(TargetPlanner)
    │                                   │ 2. BFS/A* 规划
    │                                   │ 3. pushRoute(Redis)
    │                                   │ 4. pushTask(MOVE_READY)
    │                                   │
    │ ← BLPOP taskQueue ←────────────── │ (Redis)
    │   MOVE_READY:carId               │
    │                                   │
    │── MOVE_STEP(carId) ────────────→ │ (RabbitMQ)
    │   → Car:carId                    │
```

关键：Navigator 完成后**不直接通知 Controller**，而是：

1. 把路径写入 Redis（`pushRoute`）
2. 把 `MOVE_READY` 任务推入 Redis taskQueue

Controller 通过**BLPOP 拉取** taskQueue 来获知路径已就绪。这实现了完全的**模块解耦**——Controller 和 Navigator 之间没有直接的回调/订阅关系。

## Q3：为什么 TaskConfigurator 和 Controller 要分成两个独立进程？

**考点**：理解模块拆分的原则

**回答**：

| 维度 | TaskConfigurator | Controller |
|------|-----------------|------------|
| **职责** | 一次性初始化 | 持续调度循环 |
| **生命周期** | 启动后永久等待命令 | 启动后进入双线程循环 |
| **触发频率** | 几乎为零（只在用户操作时触发） | 每 100ms 一次 |
| **崩溃影响** | 崩溃后不影响正在运行的任务（数据在 Redis） | 崩溃后任务停止 |
| **资源消耗** | 几乎为零 | CPU 持续 5-10% |

**分开的好处**：
1. **独立部署**：TaskConfigurator 可以运行在配置员的电脑上，Controller 运行在主机上
2. **崩溃隔离**：TaskConfigurator 崩溃不影响正在跑的任务
3. **权限控制**：TaskConfigurator 接收配置命令，Controller 只处理调度——两者可以有不同的访问权限
4. **独立扩缩**：Controller 可以多实例，TaskConfigurator 不需要

## Q4：RabbitMQ 和 Redis 在系统中各扮演什么角色？为什么需要两个中间件？

**考点**：理解两种中间件的不同用途

**回答**：

```
Redis（黑板/共享存储）：
  ├─ 地图状态（map:view bitmap）  → 多模块共享的"真相"
  ├─ 小车状态（car:*）            → 多模块读写
  ├─ 任务队列（taskQueue）        → Controller 拉取
  ├─ 未探索索引（unexplored:set） → TargetPlanner O(1) 选目标
  ├─ 分布式锁（lock:car:*）       → 互斥控制
  └─ 回放快照（replay:snapshots） → 录制存储

RabbitMQ（消息总线/命令管道）：
  ├─ NAVIGATE → Navigator4CarID   → 一对一命令
  ├─ MOVE_STEP → Car:{carId}      → 一对一命令
  ├─ FORWARD_CONFIG → TaskConfigCmd → 一对一命令
  └─ REFRESH_ALL → UpdateView Fanout → 一对多广播
```

**为什么不能只用 Redis？**
- Redis 不支持 Fanout 广播（需要所有 Display 实例同时收到刷新信号）
- Redis Pub/Sub 不可靠（断连期间的消息丢失）
- RabbitMQ 的持久化 + 自动恢复 + 手动确认提供了可靠的消息投递

**为什么不能只用 RabbitMQ？**
- RabbitMQ 不提供丰富的数据结构（Hash、Bitmap、Set、Sorted Set）
- 像 `BITCOUNT`、`SRANDMEMBER`、Pipeline 批量操作这些 Redis 专有操作，RabbitMQ 没有
- 分布式锁需要原子操作，RabbitMQ 不适合

# 二、数据结构与存储类

---

## Q6：为什么不直接用二维数组存储地图探索状态，而要用 Redis Bitmap？

**考点**：分布式系统中数据共享的设计

**回答**：

如果每个模块在本地内存中维护自己的二维数组（`boolean[40][40]`）：

```
Controller 本地：explored = boolean[40][40]
Navigator 本地：explored = boolean[40][40]
Car 本地：      explored = boolean[40][40]
Display 本地：  explored = boolean[40][40]
```

**问题**：
1. **数据不一致**：Car 移动后更新本地数组，但 Navigator 本地数组没更新 → 路径规划用旧数据
2. **无法跨进程共享**：不同进程的本地内存彼此隔离
3. **崩溃丢失**：进程崩溃后本地数据全丢

**Redis Bitmap 的优势**：
1. **单一数据源**：所有模块读同一个 `map:view` bitmap，天然一致
2. **持久化**：Redis RDB 快照，崩溃后可恢复
3. **高效**：40×40=1600 bits = 200 字节，`GETBIT` O(1)，`BITCOUNT` 统计 O(字节数)
4. **支持 Pipeline**：一次网络往返批量写入 9 个 SETBIT

## Q7：`unexplored:set` 的作用是什么？如果不用它会怎样？

**考点**：理解性能优化的关键数据结构

**回答**：

`unexplored:set` 是一个 Redis Set，存储所有尚未探索的坐标（格式 `"x,y"`）。

**它的核心作用**：让 TargetPlanner 能够在 **O(1)** 时间内随机获取一个未探索坐标。

**如果没有它**，TargetPlanner 选择目标需要：
```
遍历 40×40=1600 个格子
→ 排除已探索的
→ 排除障碍物
→ 排除其他车已认领的
→ 计算距离每个候选目标的距离
→ 选最近的

时间复杂度：O(1600) = 每次选目标遍历 1600 格
```

**有了它**：
```
SRANDMEMBER unexplored:set → O(1) 随机获取
→ 计算距离 → 贪心选最近的
→ SREM(选中的) → 已认领

时间复杂度：O(1)
```

100ms per tick × 4 cars = 每秒 40 次选目标 → O(1) vs O(1600) 差异非常显著。

**维护成本**：极低。每次点亮新格子（`illuminateArea`）或放置障碍物时，同步 SREM 对应的坐标。这笔开销在 Pipeline 批处理中几乎可以忽略。

## Q8：Bitmap 版本号缓存是怎么工作的？解决了什么问题？

**考点**：理解缓存失效机制

**回答**：

**问题背景**：`getMapView()` 方法在每 100ms 的 tick 中都被调用（用于快照录制和探索率计算）。如果每次都从 Redis GET 整个 bitmap + 解码 1600 个 bit：

```
每次 tick:
  GET map:view         → 200 字节网络传输（~0.5ms）
  decodeBitmap()       → 1600 次位运算（~0.5ms）
  总计：~1ms

100ms per tick → CPU 占用 1%
```

虽然不高，但可以通过缓存优化到近乎零。

**版本号缓存机制**：

```
写入端（illuminateArea / setMapViewBit）：
  Pipeline SETBIT ...            ← 写入 bitmap
  Pipeline INCR map:view:version ← 递增版本号
  Pipeline.sync()

读取端（getMapView）：
  读取 version = GET map:view:version
  
  if (缓存版本号 == version) {
      return 缓存的 boolean[][];     ← 缓存命中！不用 GET + 解码
  } else {
      缓存字节 = GET map:view;         ← 缓存失效，重新读取
      缓存版本号 = version;
      return decodeBitmap(缓存字节);    ← 解码并缓存
  }
```

**效果**：
- 车移动时（每 100ms 约 1-2 次）：缓存失效，正常 GET + 解码
- 车不动时（大部分时间）：缓存命中，直接返回，成本几乎为零

## Q9：小车路径的 LPUSH/RPOP 设计有什么巧妙之处？

**考点**：理解 Redis List 的操作方向与路径消费的关系

**回答**：

路径存储采用了看似"反向"的操作：

```java
// 写入（Navigator）
pushRoute:  DEL key →  LPUSH [第一步, 第二步, 第三步, ..., 最后一步]
//           List 变为:  [最后一步, ..., 第三步, 第二步, 第一步]

// 消费（Car）
popNextStep: RPOP key  → 弹出"第一步"（因为 LPUSH 使它到了最右边）
```

**为什么这样设计？**

如果用 `RPUSH` + `LPOP`：

```java
RPUSH [第一步, 第二步, 第三步]
LPOP → 弹出"第一步" ✓
```

也能工作，但有一个问题：**查看下一步**时：

```java
// LPUSH/RPOP 设计
peekNextStep: LRANGE -1 -1  → 取最后一个元素 → "下一步"
// 简单！只取一个元素

// RPUSH/LPOP 设计
peekNextStep: LRANGE 0 0    → 取第一个元素 → "下一步"
// 效果一样，但视觉效果不直观
```

其实两种方案功能等价。选择 `LPUSH/RPOP` 更多是因为**语义清晰**：LPUSH 是把路径"塞进去"，RPOP 是"从底部搓出来"，在直觉上是"推入"和"取出"的关系。

实际更重要的一点是：**先 DEL 再 LPUSH** 保证了路径的原子替换——旧路径被完全清除后新路径一次性写入，不会出现"新旧路径混杂"的中间状态。

## Q10：`config:task` Hash 中存了什么？`taskActive` 字段的作用是什么？

**考点**：理解配置管理

**回答**：

```redis
HGETALL config:task

{
  "mapWidth": "40",
  "mapHeight": "40",
  "carCount": "4",
  "cars": "[\"Car001\",\"Car002\",\"Car003\",\"Car004\"]",
  "obstacleDensity": "0.1",
  "routeAlgorithm": "BFS",
  "taskActive": "0"     ← 0=未激活, 1=已激活
}
```

**`taskActive` 字段的核心作用**：

它是 Controller 和 Display 之间的"**跨进程协调信号**"。

```
场景 1：用户点击"开始"
  Display → bb.setTaskActive(true)          → Redis taskActive=1
  Controller taskProcessLoop → 检查 Redis   → 发现 taskActive=1
  Controller → taskActive=true              → 开始处理任务

场景 2：探索完成
  Controller broadcastTick → 发现完成
  Controller → bb.setTaskActive(false)      → Redis taskActive=0
  Display → 读取 taskActive=0              → 前端显示"已完成"
```

**为什么存 Redis 而不是用 RabbitMQ？**
- RabbitMQ 消息是"发送即忘"，Display 无法查询"当前是否活跃"
- Redis 是持久化存储，Display 可以在任何时候读取最新状态
- 多个 Display 实例可以同时看到一致的 taskActive 值

## Q11：从用户点"开始"到第一辆车开始移动，经历了哪些步骤？

**考点**：能否完整追踪消息流

**回答**：

```
步骤 1：用户点击"开始"
  Display → Redis RPUSH taskQueue: {"type":"START"}

步骤 2：Controller 拉取 START
  BLPOP taskQueue → {"type":"START"}
  → handleStartTask()
  → 检查 config:task → 存在 → setTaskActive(true)
  → wakeTaskProcessor()

步骤 3：Controller 拉取 ROUTE_NEEDED:Car001
  BLPOP taskQueue → {"type":"ROUTE_NEEDED","carId":"Car001"}
  → processTask → requestNavigate("Car001")
  → RabbitMQ publish "Navigator4CarID": {"cmd":"NAVIGATE","data":{"carId":"Car001"}}

步骤 4：Navigator 处理 NAVIGATE
  收到 NAVIGATE
  → 读 car:Car001:position → (10,10)
  → 读 car:Car001:target → null（还没选目标）
  → 发 GET_TARGET → TargetPlannerCmd

步骤 5：TargetPlanner 选择目标
  收到 GET_TARGET
  → SRANDMEMBER unexplored:set → 未探索坐标
  → 选最近格 → 写 car:Car001:target
  → RPUSH taskQueue: {"type":"ROUTE_NEEDED","carId":"Car001"}

步骤 6：Controller 再次拉取 ROUTE_NEEDED
  BLPOP → ROUTE_NEEDED:Car001
  → requestNavigate("Car001")
  → NAVIGATE → Navigator4CarID

步骤 7：Navigator 规划路径
  收到 NAVIGATE
  → 读 position (10,10) + target (15,12) + map:blocked
  → BFS 规划: [(10,10)→(11,10)→...→(15,12)]
  → pushRoute(Car001, path)
  → setCarStatus(Car001, IDLE)
  → RPUSH taskQueue: {"type":"MOVE_READY","carId":"Car001"}

步骤 8：Controller 拉取 MOVE_READY
  BLPOP → MOVE_READY:Car001
  → 双层暂停检查 → 通过
  → RabbitMQ publish "Car:Car001": {"cmd":"MOVE_STEP","data":{"carId":"Car001"}}

步骤 9：Car 执行移动
  收到 MOVE_STEP
  → peekNextStep → (11,10)
  → 检查无障碍 → popNextStep
  → 更新位置 → illuminateArea(11,10) → 步数+1
  → 瞬时广播 REFRESH_ALL

总耗时：约 3-5ms（不含网络延迟）
```

## Q12：为什么 taskQueue 用 Redis List 而不是 RabbitMQ 队列？

**考点**：技术选型的深度理解

**回答**：

| 维度 | Redis List | RabbitMQ Queue |
|------|-----------|---------------|
| **拉取方式** | BLPOP 阻塞拉取 | basicConsume 回调推 |
| **控制权** | 消费者控制拉取速度 | 生产者/中间件控制推送速度 |
| **队列可见性** | `LLEN taskQueue` 随时可查 | 需要额外 API |
| **积压处理** | 积压只影响 Redis 内存 | 积压影响 RabbitMQ 内存+磁盘 |
| **配置复杂度** | 零配置，开箱即用 | 需要声明队列、Exchange、绑定 |

**选择 Redis List 的关键原因**：Controller 需要**精确控制自己的处理节奏**。

如果 taskQueue 是 RabbitMQ 队列，当 Controller 处理慢时：
- 消息积压在 RabbitMQ → 可能触发流控 → 影响其他队列（如 MOVE_STEP）
- Controller 无法"反压"——它只能被迫接收消息

Redis List 的 BLPOP 给 Controller 提供了天然的**背压机制**：
- 处理完一条 → 才拉下一条
- 如果想快 → 连续 LPOP 清空
- 如果想慢 → BLPOP 等 2 秒

## Q13：Controller 的连续清空（Drain Loop）是什么？为什么要这样做？

**考点**：理解性能优化细节

**回答**：

```java
// taskProcessLoop 中的代码
Map<String, String> task = bb.blockingPopTask(2);  // BLPOP 阻塞拉一条
if (task != null) {
    processTask(task);
    // ⬇ 连续清空
    Map<String, String> next;
    while ((next = bb.popTask()) != null) {  // LPOP 非阻塞连续拉
        processTask(next);
    }
}
```

**没有连续清空的问题**：

```
时间 T1: BLPOP 拉到 ROUTE_NEEDED:Car001 → 开始处理
时间 T2: 在处理过程中，Navigator 推入了 MOVE_READY:Car001
时间 T3: processTask 处理完 ROUTE_NEEDED → 回到 BLPOP(2)
时间 T4: BLPOP 立即返回 MOVE_READY（因为列表非空）
时间 T5: processTask 处理 MOVE_READY

T2到T5的延迟：~1ms（非常小，可以接受）
```

**但连续清空解决了另一个问题**：

```
场景：4 辆车同时完成了路径规划，taskQueue 中有 4 个 MOVE_READY
  BLPOP 拉第一条 → 处理 → BLPOP 拉第二条 → 处理 → ...

问题：每处理一条就要一次 BLPOP 网络往返（~0.5ms）
     4 个 MOVE_READY 需要 4 次网络往返 = 2ms

连续清空：
  BLPOP 拉第一条 → 处理 → LPOP 拉第二条 → 处理 → LPOP 拉第三条...
  1 次 BLPOP + 3 次 LPOP = 1+3×0.5 = 2.5ms
  vs 4 次 BLPOP = 4×0.5 = 2ms

差异不大，但处理更多任务时优势明显（如 20 个任务）
  连续清空：BLPOP×1 + LPOP×19 = 10ms
  逐条 BLPOP：BLPOP×20 = 10ms

实际上差异在低负载时不显著，但连续清空保证了"不会因为 BLPOP 的阻塞超时
而延迟处理已经在队列中的任务"。
```

**真正的价值**：如果 Controller 处理一条任务时，有 10 条新任务被推入。连续清空确保这 10 条被立即处理，而不是等到下一轮 BLPOP（最坏等 2 秒）。

## Q14：`processTask` 中处理 MOVE_READY 前为什么要做双层暂停检查？

**考点**：理解多用户协作的并发控制

**回答**：

```
双层暂停 = 全局暂停 + 个人暂停

全局暂停（配置员操作）：
  bb.setGlobalPause(true)  → Redis SET pause:global "true"
  效果：所有车都停

个人暂停（运行员操作）：
  bb.setOperatorPause("B", true) → Redis SET pause:operator:B "true"
  效果：只有 machine="B" 的车停
```

**检查顺序有讲究**：

```java
if (bb.isGlobalPaused()) break;            // 第 1 层：全局
String owner = bb.getCarOwner(carId);
if (owner != null && bb.isOperatorPaused(owner)) break;  // 第 2 层：个人
```

**先全局、后个人**的设计保证了：

1. **全局暂停覆盖一切**：如果全局暂停，不管 owner 是谁，车都停
2. **短路求值**：全局暂停时直接 break，不检查个人（节省一次 Redis EXISTS 调用）

**没有双层暂停会怎样？**

如果只有全局暂停：
- 配置员暂停后，所有运行员的车都停 → 运行员无法单独控制

如果只有个人暂停：
- 要在 4 个运行员面板上逐个点暂停才能全停 → 配置员效率极低

## Q15：Controller 有两个"推车"入口：`processTask(MOVE_READY)` 和 `tickDriveCars()`，它们是什么关系？

**考点**：理解事件驱动 + 定时驱动的互补设计

**回答**：

```
入口 1：processTask(MOVE_READY)
  └─ 任务队列驱动的"第一步"
  └─ Navigator 规划完路径 → 推 MOVE_READY → Controller 拉取 → 发 MOVE_STEP
  └─ 作用：车刚拿到新路径后，立刻走第一步

入口 2：tickDriveCars()
  └─ 100ms 定时器驱动的"后续步"
  └─ 遍历所有 IDLE 车 → 如果还有路径 → 发 MOVE_STEP
  └─ 作用：上一步走完后，自动走下一步
```

**为什么需要两个入口？**

小车每次收到 MOVE_STEP 后：
1. 走一步 → 设为 IDLE
2. 不会主动推新任务到 taskQueue

如果只有入口 1（任务驱动），车走完一步后就**停住了**——必须等 Navigator 重新规划路径、推新的 MOVE_READY。但实际上下一步已经在前面的路径中了！

所以入口 2（定时驱动）检查 IDLE 的车："你路径里还有下一步吗？有就继续走。"

**两者的时序关系**：

```
Tick 1:  BLPOP → MOVE_READY → 发 MOVE_STEP → Car001 走第 1 步 → IDLE
Tick 1:  tickDriveCars → peekNextStep → 有第 2 步 → 发 MOVE_STEP → 走第 2 步
Tick 2:  tickDriveCars → peekNextStep → 有第 3 步 → 发 MOVE_STEP → 走第 3 步
...
Tick N:  tickDriveCars → peekNextStep → null → 路径走完
```

**注意**：同一个 tick 内，`processTask` 先执行（BLPOP），`tickDriveCars` 后执行（广播中）。所以第 1 步和可能的第 2 步可以在同一个 100ms 周期内完成。

## Q16：为什么 REFRESH_ALL 通过 Fanout Exchange 广播，而其他命令走普通队列？

**考点**：理解广播 vs 点对点的不同场景

**回答**：

```
NAVIGATE → Navigator4CarID      → 点对点（只有一个或少数 Navigator 消费）
MOVE_STEP → Car:Car001          → 点对点（只有 Car001 消费）
FORWARD_CONFIG → TaskConfigCmd  → 点对点（只有 TaskConfigurator 消费）
REFRESH_ALL → UpdateView Fanout → 广播（所有 Display 实例都需要收到）
```

**Fanout 的选择逻辑**：

- REFRESH_ALL 需要**所有 Display 实例同时收到**（因为每个 Display 连接着不同的浏览器）
- 如果用普通队列，需要为每个 Display 创建独立队列并逐个发送 → 复杂且不同步
- Fanout Exchange 一条消息就能发给所有绑定的队列

**只有 instanceId=0 的 Controller 广播**：

```java
private void broadcastViewRefresh() {
    if (instanceId != 0) return;  // 只有主实例广播
    // ...
}
```

如果所有 Controller 实例都广播，Display 会收到多条重复的 REFRESH_ALL → 前端多次重绘 → 浪费资源。

## Q17：多实例 Controller 如何保证互不冲突？分片规则是什么？

**考点**：理解分布式分片

**回答**：

**分片规则**：按小车在 `cars` 列表中的索引取模：

```java
private boolean isMyCar(List<String> carIds, String carId) {
    if (totalInstances <= 1) return true;        // 单实例 → 全部归我
    int idx = carIds.indexOf(carId);
    return idx >= 0 && (idx % totalInstances) == instanceId;
}
```

**示例**：2 个实例，4 辆车：

```
cars = [Car001, Car002, Car003, Car004]
索引:      0       1       2       3

实例 0 (instanceId=0)：索引 0,2 → Car001, Car003
实例 1 (instanceId=1)：索引 1,3 → Car002, Car004
```

**分片在哪里生效？**

分片检查出现在 3 个位置：

| 位置 | 作用 |
|------|------|
| `processTask()` | 车辆任务只处理归我的车（ROUTE_NEEDED、MOVE_READY 等） |
| `tickDriveCars()` | 只驱动归我的 IDLE 车 |
| `fallbackBlockedCheck()` | 只检查归我的 BLOCKED 车 |

**三处都用分片，确保不同的实例不会同时操作同一辆车。**

**如果一辆车的索引变了怎么办（比如删了车）？**

删除车只会从 cars 列表中移除该车，不影响其他车的索引。新增车追加到列表末尾，新索引由当前实例数重新分片。

## Q18：分布式锁在什么场景下使用？为什么受阻恢复需要用锁？

**考点**：理解分布式锁的适用场景

**回答**：

**项目中的使用场景**：`handleBlockedTimeout()` —— 受阻超时恢复。

**为什么需要锁？**

```
场景：两个 Controller 实例同时检测到 Car001 被阻塞

实例 0（tick=102）:                   实例 1（tick=102）:
  fallbackBlockedCheck()               fallbackBlockedCheck()
  → Car001 是 BLOCKED                 → Car001 是 BLOCKED
  → handleBlockedTimeout("Car001")     → handleBlockedTimeout("Car001")
  → diff = 2 ≥ 2 → 触发恢复            → diff = 2 ≥ 2 → 触发恢复

如果不加锁：
  实例 0: clearCarRoute("Car001")      实例 1: clearCarRoute("Car001")
  实例 0: clearCarTarget("Car001")     实例 1: clearCarTarget("Car001")
  实例 0: setCarStatus(IDLE)           实例 1: setCarStatus(IDLE)
  实例 0: pushTask(ROUTE_NEEDED)       实例 1: pushTask(ROUTE_NEEDED)
  
  结果：ROUTE_NEEDED 被推了 2 次！
       → Navigator 可能同时规划 2 条路径
       → Car001 收到 2 条 MOVE_STEP
       → 车可能走错路！

加上锁：
  实例 0: tryLock("lock:car:Car001") → ✅ 拿到锁
  实例 1: tryLock("lock:car:Car001") → ❌ 被占用，放弃
  实例 0: 执行恢复 → unlock()
```

**锁的生命周期**：

```
1. tryLock()  → SET lock:car:Car001 "thread-123" NX EX 30
2. 执行临界区代码（~1ms）
3. unlock()   → Lua: if get == "thread-123" then del
```

即使步骤 2 中进程崩溃了，锁也会在 30 秒后自动过期（EX 30），不会死锁。

## Q19：Controller 的双线程（taskProcessor + broadcastScheduler）之间如何协调？

**考点**：理解线程间通信机制

**回答**：

```
taskProcessor 线程：
  while(running) {
    if (!taskActive) wait(1000);
    BLPOP → processTask → 连续 LPOP
  }

broadcastScheduler 线程（每 100ms）：
  broadcastTick() {
    探索完成判定 → 如果完成 → taskActive=false → wakeTaskProcessor()
    tickDriveCars()
    broadcastViewRefresh()
  }
```

**协调机制**：

| 变量 | 谁写 | 谁读 | 保护方式 |
|------|------|------|---------|
| `running` | `stop()` | 两个线程 | `volatile` |
| `taskActive` | `handleStartTask/PauseTask/broadcastTick` | `taskProcessLoop` | `volatile` |
| `recording` | `processTask(RECORD_START/STOP)` | `broadcastTick` | `volatile` |
| `tickCount` | `broadcastTick` | 只有 broadcastTick 自己用 | 不需要 volatile |

**wake/notify 机制**：

```java
// taskProcessLoop 中
synchronized (taskWakeLock) {
    taskWakeLock.wait(1000);    // 释放锁，休眠
}

// handleStartTask / broadcastTick 中
synchronized (taskWakeLock) {
    taskWakeLock.notifyAll();   // 唤醒 wait 中的线程
}
```

`wait/notify` 保证：当 taskActive 被设为 true 时，taskProcessLoop 能在**亚毫秒级**内被唤醒并开始工作。

## Q20：`volatile` 关键字在 Controller 中的作用是什么？如果去掉会怎样？

**考点**：理解 Java 内存模型和可见性问题

**回答**：

```java
private volatile boolean running = false;
private volatile boolean taskActive = false;
private volatile boolean recording = false;
```

**`volatile` 的作用**：保证变量的读写对所有线程立即可见。

**为什么需要它？**

Java 内存模型中，每个线程有自己**本地 CPU 缓存**：

```
线程 A（taskProcessor）              线程 B（broadcastScheduler）
     │                                       │
  CPU 缓存: taskActive=false             CPU 缓存: taskActive=true ← 刚改了
     │                                       │
     └───────── 主内存 ──────────────────────┘
```

如果没有 `volatile`：
- 线程 B 修改 `taskActive=true`
- 这个修改可能只写入了线程 B 的 CPU 缓存
- 线程 A 读到的是自己 CPU 缓存中的旧值 `false`
- → 线程 A 一直以为任务没激活，永远在 wait

**加上 `volatile`**：
- 线程 B 修改后，值**立即刷新到主内存**
- 线程 A 读取时，**强制从主内存读取**
- → 线程 A 立即看到 `taskActive=true`

## Q21：TaskConfigurator 有没有并发问题？

**考点**：全面审视并发安全性

**回答**：

**基本没有**。

TaskConfigurator 是**单线程事件模型**：

```java
channel.basicConsume(TASK_CONFIG_QUEUE, false, deliverCallback, consumerTag -> {});
```

RabbitMQ 保证**同一个 Channel 的消息串行处理**——`deliverCallback` 在同一时间只有一个在执行。

**唯一的潜在冲突**：TaskConfigurator 执行全量初始化（`clearAll` + 重建）时，其他模块可能在读写 Redis。

```
时间 T1: TaskConfigurator 执行 clearAll()
时间 T2: Controller 正在 BLPOP taskQueue → 突然 taskQueue 被删了 → 返回 null
时间 T3: Controller 认为"队列为空"，进入下一轮 BLPOP 等待
时间 T4: TaskConfigurator 重建完成 → 新的 taskQueue 已就绪
时间 T5: Controller 下一轮 BLPOP → 正常获取任务
```

这种"短暂不一致"是可以接受的——Controller 通过循环自动恢复。

## Q22：如果 Redis 突然挂了，Controller 会怎样？能自动恢复吗？

**考点**：理解容错恢复机制

**回答**：

**Redis 宕机时**：

```
taskProcessLoop 中的 BLPOP 抛异常（连接断开）
→ catch (Exception e) { sleep(500); }
→ while(running) 重新循环
→ BLPOP 重试 → 如果 Redis 恢复了 → 正常
→ 如果 Redis 还没恢复 → 继续 sleep(500) → 重试

broadcastTick 中的 GETBIT/BITCOUNT 也抛异常
→ catch (Exception e) { log.error(...); }
→ 本次 tick 失败 → 100ms 后重试
```

**自动恢复能力**：✅ 有。Controller 通过循环 + sleep(500) 实现了自动重连。

**但恢复后的问题**：Redis 重启后数据可能丢失（取决于是否持久化）。如果数据丢了：
- TaskConfigurator 的崩溃恢复机制会检测到 `existingConfig` 为空
- Controller 不会自动重新初始化（需要用户手动点"重置"或重启 TaskConfigurator）

## Q23：如果 RabbitMQ 突然挂了，会发生什么？

**考点**：理解 RabbitMQ 故障的影响

**回答**：

**RabbitMQ 宕机时**：

```
sendCommand(MOVE_STEP, ...):
  mq.publish("Car:Car001", json)
  → catch (IOException e) { log.error(...); }
  → 消息发送失败 → 这次 MOVE_STEP 丢失了

但车还是 IDLE 状态 → 下一个 100ms tickDriveCars 会重试发送
```

**RabbitMQ 自动恢复**：

```java
factory.setAutomaticRecoveryEnabled(true);   // 启用自动重连
factory.setNetworkRecoveryInterval(5000);     // 每 5 秒重试
```

当 RabbitMQ 恢复后，`MessageBusClient` 会自动重连并恢复 Channel。

**影响分析**：

| 模块 | 影响 | 恢复后 |
|------|------|--------|
| Controller | sendCommand 失败 | tickDriveCars 重试 |
| Navigator | 收不到 NAVIGATE | Controller 循环推 MOVE_READY 时会触发重规划 |
| Car | 收不到 MOVE_STEP | tickDriveCars 下一周期重发 |
| Display | 收不到 REFRESH_ALL | 100ms 后下一轮广播 |

**结论**：RabbitMQ 短暂宕机不会导致任务失败，系统通过重试机制自动恢复。但如果 RabbitMQ 长时间不可用，任务将停滞。

## Q24：探索完成的判定条件是什么？为什么是两个条件？

**考点**：理解"双保险"设计

**回答**：

```java
if (unexploredCount == 0 && explored >= 99.9) {
    // 巡检完成！
}
```

**两个条件必须同时满足**：

| 条件 | 数据来源 | Redis 命令 | 单条件失效场景 |
|------|---------|-----------|---------------|
| `unexploredCount == 0` | `SCARD unexplored:set` | O(1) | Redis 重启后 Set 丢失 → 误判为 0 |
| `explored >= 99.9` | `BITCOUNT map:view` | O(字节数) | 浮点精度 → 可能 99.95% |

**为什么不是 `explored == 100.0`？**

浮点计算可能产生微小误差。`BITCOUNT` 返回整数，除以 `(总格-障碍物格)` 可能不是精确的 100.0。

**为什么是 99.9 而不是 99.0？**

因为 unexplored:set 已经空了（意味着所有非障碍格都已被探索），BITCOUNT 应该已经等于可探索格数。`99.9` 提供了一个合理的容差范围。

## Q25：障碍物生成数量不够（小于目标值）怎么办？

**考点**：边界条件处理

**回答**：

```java
if (placed < targetObstacleCount) {
    LOG.warn("障碍物生成不足: 目标={}, 实际={}", targetObstacleCount, placed);
}
```

**什么情况下会不够？**

1. 地图太小（比如 10×10 = 100 格，目标 50 个，但禁区很大）
2. 出生点太多导致禁区太大
3. 极端情况下 maxAttempts 达到上限

**系统如何处理？**

只打一个 WARNING，然后**继续正常运行**。障碍物少不会导致程序崩溃——只是地图更"空旷"，探索更快完成。

**这是一个好的设计吗？**

是的。"Graceful Degradation"（优雅降级）：子功能不完全达标时，系统仍能正常工作，只是效果打折扣。

## Q26：小车被障碍物堵住超过 200ms 后，恢复流程是怎样的？

**考点**：理解受阻恢复的完整流程

**回答**：

```
时间线：

T=0ms:   Car001 在 (10,10)，下一步 (11,10) 有障碍物
         → CarAgent 设 status=BLOCKED
         → bb.setBlockedTick("Car001", tickCount=42)
         → bb.pushTask("BLOCKED", "Car001", null)

T=10ms:  Controller processTask(BLOCKED, Car001)
         → handleBlockedTimeout("Car001")
         → diff = currentTick(42) - blockedTick(42) = 0
         → 0 < 2 → 不处理（等待）

T=100ms: broadcastTick
         → fallbackBlockedCheck()
         → diff = 43 - 42 = 1 < 2 → 不处理

T=200ms: broadcastTick
         → fallbackBlockedCheck()
         → diff = 44 - 42 = 2 >= 2 → 触发恢复！
         → DistributedLock lock = bb.getCarLock("Car001")
         → lock.tryLock() → ✅
         → bb.clearCarRoute("Car001")     ← 删除旧路径
         → bb.clearCarTarget("Car001")    ← 删除旧目标
         → bb.setCarStatus("Car001", IDLE)
         → bb.pushTask("ROUTE_NEEDED", "Car001", null)
         → lock.unlock()

T=210ms: Controller processTask(ROUTE_NEEDED, Car001)
         → requestNavigate("Car001")
         → 重新开始规划...
```

**关键点**：
1. 2 tick（200ms）后才恢复，给障碍物一个"观察窗口"
2. 用分布式锁保证多实例环境下的安全
3. 恢复后清除旧路径和目标 → 重新从零开始规划

## Q27：如果 TaskConfigurator 在执行全量初始化的过程中崩溃了，Redis 会出现什么状态？

**考点**：理解崩溃一致性

**回答**：

```
全量初始化的执行顺序：
  1. clearAll()       ← 这里崩溃 → Redis 全部清空，但后续步骤没执行
  2. initUnexploredSet()
  3. computeSpawnPoints()
  4. buildForbiddenZone()
  5. generateObstacles()
  6. 初始化小车
  7. setTaskConfig()   ← 这里崩溃 → 地图有了，但 config:task 不完整
  8. pushTask(ROUTE_NEEDED)
  9. declareAllSystemQueues()
 10. bgsave()
```

**最坏情况**：在步骤 7（`setTaskConfig`）之前崩溃。

此时 Redis 中**部分数据已存在**（地图 bitmap、障碍物、小车位置），但 `config:task` Hash 不完整或不存在。

**恢复机制**：TaskConfigurator 重启后：

```java
Map<String, String> existingConfig = blackboard.getTaskConfig();
if (!forceReset && existingConfig != null && !existingConfig.isEmpty()) {
    // 跳过初始化 ← 但此时 existingConfig 可能为空或不完整！
}
```

**这是一个漏洞吗？**

是的。如果崩溃发生在 `clearAll()` 之后、`setTaskConfig()` 之前，新启动的 TaskConfigurator 会检测到 `existingConfig` 为空，然后重新执行全量初始化——这次会成功完成。所以虽然有短暂的不一致，但最终可以恢复。

如果崩溃发生在 `setTaskConfig()` 之后，existingConfig 非空，TaskConfigurator 跳过初始化，任务可以继续。

# 六、算法与策略类

---

## Q28：0-1 BFS 和普通 BFS 有什么区别？为什么选择 0-1 BFS？

**考点**：理解寻路算法的设计选择

**回答**：

普通 BFS：所有边的代价都是 1。从起点开始逐层扩展，找到的路径步数最少。但它不关心路径经过的区域是"旧"还是"新"。

0-1 BFS：边权只有 0 和 1。使用双端队列：
- cost=0 的邻居 → `offerFirst()`（优先处理）
- cost=1 的邻居 → `offerLast()`（延后处理）

**在这个项目中的应用**：

```
未探索的邻居 → cost=0 → offerFirst（优先走新区域）
已探索的邻居 → cost=1 → offerLast（不优先走老路）
```

**效果对比**：

```
普通 BFS 规划的路径：
  (10,10) → (10,11) → (10,12) → ... 可能全部走在已探索区域

0-1 BFS 规划的路径：
  (10,10) → (11,10, 未探索) → (12,10, 未探索) → ...
  优先穿过未探索区域，同时保证最短路径
```

**为什么不用 Dijkstra？**

Dijkstra 时间复杂度 O(V log V)，需要优先队列。0-1 BFS 的 O(V) 对于 1600 格的网格来说快很多（1600 vs 1600×log(1600)≈17600）。

## Q29：TargetPlanner 的"贪心最近格"策略有什么局限性？如何改进？

**考点**：理解贪心算法的优缺点

**回答**：

**当前策略**：
1. 从 `unexplored:set` 随机获取候选
2. 排除其他车已认领的目标
3. 选距离最近的一个

**优点**：
- O(1) 选目标（SRANDMEMBER）
- 简单，代码量少

**局限性**：

```
场景：车在 (10,10)，两个候选目标：(11,10) 和 (30,10)
  → 贪心选 (11,10)，距离 1
  → 但实际上 (30,10) 在一个大的未探索区域中
  → 贪心选了近的，但错过了"战略要点"
```

**可能的改进方向**：

1. **加权距离**：未探索格密度越高 → 权重越低 → 吸引车去密集未探索区域
2. **区域划分**：在 unexplored:set 中按区域分组，轮流从不同区域选目标
3. **多车协调**：在选目标时考虑其他车的位置，避免多车挤在同一区域

**为什么不现在就这样做？**

因为当前策略在 40×40 的地图上工作得很好，没有明显的性能瓶颈。过度优化是"过早优化"（premature optimization）的反模式。

## Q30：网格分区出生点算法是怎么确保车均匀分布的？

**考点**：理解空间分布算法

**回答**：

```java
int cols = (int) Math.ceil(Math.sqrt(carCount));   // 列数 = ⌈√N⌉
int rows = (int) Math.ceil((double) carCount / cols); // 行数 = ⌈N/cols⌉
int cellW = mapWidth / cols;
int cellH = mapHeight / rows;

// 每辆车放在对应格子的中心
int cx = col * cellW + cellW / 2;
int cy = row * cellH + cellH / 2;
```

**为什么用 `√N` 来决定列数？**

目标是让网格尽量"正方形"，这样车之间的最小距离最大化：

```
N=4: cols=2, rows=2 → 2×2 正方形 → 车分布在四角 → 最大间距
N=5: cols=3, rows=2 → 3×2 矩形 → 5 辆车分散在 6 个格子中
N=8: cols=3, rows=3 → 3×3 正方形 → 8 辆车分散在 9 个格子中
```

**如果随机放置呢？**

4 辆车随机放在 40×40 地图上：
- 可能 4 辆全在左上角 → 它们互相竞争同一批未探索格
- 也可能分布得好 → 但无法保证

网格分区保证了下限——车之间的距离至少有一个 cell 的跨度。

## Q31：为什么 BLOCKED_TIMEOUT_TICKS = 2（200ms）？为什么不是 0 或 10？

**考点**：理解参数调优的 trade-off

**回答**：

| 值 | 行为 | 问题 |
|----|------|------|
| **0 tick** | 一堵就立即恢复 | 车可能被暂时性障碍堵住（其他车经过），立即清路径太激进，浪费了已规划好的路径 |
| **2 ticks** | 200ms 观察窗口 | 给暂时性障碍留一点时间解除，平衡了响应速度和稳定性 |
| **10 ticks（1秒）** | 等 1 秒 | 如果障碍是永久性的（静态障碍物），白白浪费 1 秒 |

**为什么是 200ms？**

在实际测试中，车之间的"动态阻塞"（两车交叉移动时短暂挡住对方）通常在 1-2 个 tick 内自行解除。200ms 刚好覆盖了这个窗口。

**什么情况下应该调整这个值？**

- 小车移动速度更快（tick 更短）：调大（如 5 ticks）
- 小车移动速度更慢：可以保持 2 ticks
- 障碍物非常密集：调小（如 1 tick），快速重规划

# 七、性能与优化类

## Q32：为什么障碍物批量写入用 Pipeline？带来了多少性能提升？

**考点**：理解 Redis Pipeline 的性能优势

**回答**：

**不用 Pipeline**：

```java
for (Point obs : obstacles) {
    jedis.setbit("map:blocked", offset, true);   // 网络往返 0.5ms
    jedis.srem("unexplored:set", "x,y");          // 网络往返 0.5ms
}
// 160 个障碍物 × 2 个命令 × 0.5ms = 160ms
```

**用 Pipeline**：

```java
Pipeline pipeline = jedis.pipelined();
for (Point obs : obstacles) {
    pipeline.setbit("map:blocked", offset, true);  // 攒在本地
    pipeline.srem("unexplored:set", "x,y");         // 攒在本地
}
pipeline.sync();  // 一次性发送 320 条命令 → 1 次网络往返 0.5ms
// 总耗时：~0.5ms
```

**性能提升**：160ms → 0.5ms，约 **320 倍**。

**Pipeline 的本质**：减少网络往返次数（Round Trip Time），这是 Redis 性能优化的第一原则。

## Q33：Controller 的 100ms tick 周期是怎么定下来的？能改成 50ms 吗？

**考点**：理解 tick 周期的 trade-off

**回答**：

**100ms 的选择理由**：

1. **视觉流畅**：用户看到的动画更新频率 10 FPS，已经够流畅
2. **CPU 友好**：tick 耗时 ~5ms，CPU 占用约 5%
3. **网络友好**：每次 tick 发一次 REFRESH_ALL，10 次/秒不产生网络压力
4. **车移动节奏**：车一次走一格，100ms 的步频在视觉上清晰可辨

**如果改成 50ms**：
- 动画更流畅（20 FPS）
- CPU 占用翻倍（~10%）
- 车移动更快（每 50ms 一步）→ 可能需要调整 BLOCKED_TIMEOUT_TICKS

**如果改成 200ms**：
- 动画有卡顿感
- CPU 占用更低
- 车移动更慢 → 探索时间更长

**100ms 是一个合理的平衡点。**

## Q34：Bitmap 版本号缓存对性能有多大的提升？

**考点**：量化缓存的性能收益

**回答**：

**没有缓存**（每次 tick 都 GET + 解码）：

```
getMapView():
  GET map:view (200 bytes)   → ~0.5ms
  decodeBitmap (1600 bits)   → ~0.5ms
  总计：~1ms per call

getMapBlocked():
  GET map:blocked (200 bytes)→ ~0.5ms
  decodeBitmap (1600 bits)   → ~0.5ms
  总计：~1ms per call

每 tick：~2ms（两次 bitmap 读取）
saveSnapshotIfRecording 中额外调用：~2ms
总计：~4ms per tick
CPU 占用：4ms/100ms = 4%
```

**有缓存**（多数 tick 命中缓存）：

```
车不动时（95% 的 tick）：
  getMapView(): GET version → 版本号未变 → 返回缓存 → ~0.1ms
  getMapBlocked(): GET version → 版本号未变 → 返回缓存 → ~0.1ms
  总计：~0.2ms per tick

车移动时（5% 的 tick）：
  getMapView(): 缓存失效 → GET + 解码 → ~1ms
  总计：~1ms per tick

平均：0.95×0.2 + 0.05×1 = ~0.24ms per tick
vs 无缓存：4ms

性能提升：~16x
CPU 占用下降：4% → 0.24%
```

## Q35：整个系统最大的性能瓶颈在哪里？

**考点**：全局性能视角

**回答**：

按重要性排序：

| 瓶颈 | 影响 | 优化空间 |
|------|------|---------|
| **1. 寻路算法** | 每次 BFS 遍历 1600 格，多辆车同时规划时 CPU 压力大 | 可以缓存已规划路径、增量规划 |
| **2. 快照录制** | 每 100ms 序列化 4KB JSON + RPUSH | 可以降采样（每 500ms 一帧） |
| **3. Redis 网络延迟** | 每次 Redis 操作 0.5ms，tick 中有多次调用 | 已经做了 Pipeline 和版本号缓存 |
| **4. RabbitMQ Fanout** | 广播给所有 Display | 合理（必须的） |
| **5. 前端 Canvas 渲染** | 每 100ms 渲染 1600 个矩形 | JS 已经做了优化，2-3ms |

**当前系统的最大瓶颈**：寻路算法，特别是在多辆车同时需要规划时。但 0-1 BFS 的 O(V) 复杂度对于 1600 格的网格来说已经足够快。

## Q36：请完整描述：用户打开浏览器 → 点"应用配置" → 点"开始" → 车移动 → 探索完成，整个过程中 Controller 做了什么？

**考点**：全链路追踪能力

**回答**：

```
阶段 1 — 初始化
═══════════════════════════════════════════════════

用户：点"应用配置"
  → Display WebSocket → Redis RPUSH taskQueue: {"type":"SET_CONFIG",...}
  
Controller: BLPOP → SET_CONFIG
  → handleSetConfigTask()
  → 构造 FORWARD_CONFIG(active=false)
  → RabbitMQ publish TaskConfigCmd

TaskConfigurator: 收到 FORWARD_CONFIG
  → clearAll() + 地图初始化 + 障碍物 + 小车
  → setTaskConfig(taskActive=0)
  → 推 4 个 ROUTE_NEEDED → taskQueue
  → BGSAVE

阶段 2 — 启动
═══════════════════════════════════════════════════

用户：点"开始"
  → Display → Redis RPUSH taskQueue: {"type":"START"}

Controller: BLPOP → START
  → handleStartTask()
  → config:task 存在 → setTaskActive(true) → taskActive=true
  → wakeTaskProcessor()

Controller: BLPOP → ROUTE_NEEDED:Car001
  → requestNavigate → NAVIGATE → Navigator4CarID

阶段 3 — 循环（对每辆车重复）
═══════════════════════════════════════════════════

Navigator: 收到 NAVIGATE
  → 没目标 → GET_TARGET → TargetPlanner
TargetPlanner: 选目标 → 写 target → ROUTE_NEEDED
Controller: BLPOP → ROUTE_NEEDED → NAVIGATE
Navigator: 有目标 → BFS 规划 → pushRoute → MOVE_READY
Controller: BLPOP → MOVE_READY → MOVE_STEP → Car
Car: popNextStep → 移动 → illuminateArea → REFRESH_ALL

（重复 ~N 次 tick）

阶段 4 — 完成
═══════════════════════════════════════════════════

Controller broadcastTick:
  → SCARD unexplored:set → 0
  → BITCOUNT explored → 1440
  → explored% = 1440/(1600-160)=100%
  → explored >= 99.9% ✓
  → 两个条件都满足 → 完成！
  → taskActive=false → setTaskActive(false) → recording=false
  → REFRESH_ALL(completed=true)
  → Display 显示 "巡检完成"
```

## Q37：如果用户在任务运行时点了"重置"，Controller 内部发生了什么？

**考点**：理解中断和重建流程

**回答**：

```
用户点"重置"
  → Display → Redis RPUSH taskQueue: {"type":"RESET",...}

Controller: BLPOP → RESET
  → handleResetTask(task)
  → 构造 FORWARD_CONFIG(forceReset=true, active=false)
  → userActivated=false
  → taskActive=false              ← 停止处理新任务
  → recording=false               ← 停止录制
  → try { DEL replay:snapshots }  ← 清除旧快照
  → tickCount=0                   ← 重置计数器
  → clearTaskQueue()              ← 清空旧任务
  → RabbitMQ publish TaskConfigCmd

TaskConfigurator: 收到 FORWARD_CONFIG(forceReset=true)
  → 检测到 existingConfig 存在
  → 但 forceReset=true → 跳过崩溃恢复
  → clearAll() + 全量初始化       ← 重建一切
  → setTaskConfig(taskActive=0)
  → 推 4 个 ROUTE_NEEDED
  → BGSAVE

此时：Redis 中是新地图、新障碍物、新车位
      Controller taskActive=false，等待用户再次"开始"
```

## Q38：假设现在有 2 个 Controller 实例、4 辆车，实例 0 崩溃了，实例 1 会接管所有车吗？

**考点**：理解多实例故障切换

**回答**：

**不会自动接管**。分片规则是静态的：

```
崩溃前：
  实例 0：Car001(索引0), Car003(索引2)
  实例 1：Car002(索引1), Car004(索引3)

实例 0 崩溃后：
  实例 1 仍只处理 Car002 和 Car004
  Car001 和 Car003 无人处理
  → 这两辆车如果 IDLE 且有路径，tickDriveCars 不会驱动它们
  → 它们会停在原地
```

**为什么会这样设计？**

分片规则基于"小车索引在 cars 列表中的位置"，这个位置在运行中不改变。实例 0 崩溃不会改变列表，所以实例 1 不会接管。

**如何改进？**

可引入**主备（Leader-Follower）机制**：
1. 每个实例有主备角色，通过 Redis 分布式锁选举 Leader
2. Leader 崩溃后，Follower 检测到锁过期 → 竞选新 Leader → 接管全部车
3. 或者引入**一致性哈希**动态重新分配

**当前实现为什么没做？**

因为分片是为了**负载均衡**而非高可用。多实例场景主要用于多台电脑分担计算压力（每台电脑上运行 Navigator + Car），而非故障切换。

## Q39：从代码中你能看出哪些地方是"为了生产环境"做的设计？哪些是"原型阶段"的简化？

**考点**：工程判断力

**回答**：

**生产级设计**：

| 设计 | 体现 |
|------|------|
| 分布式锁 + Lua 脚本 | 原子释放，防死锁 |
| 双层暂停 | 多用户协同控制 |
| 崩溃恢复 | TaskConfigurator 重启后跳过初始化 |
| 版本号缓存 | bitmap 读取性能优化 |
| Pipeline 批处理 | 障碍物写入 320x 提升 |
| try-finally 释放锁 | 异常安全 |
| volatile + synchronized | 线程安全 |
| BGSAVE 持久化 | Redis 数据可恢复 |
| 守护线程 | JVM 正常退出 |
| 异常保护 + 重试 | Redis 短暂不可用自动恢复 |

**原型阶段简化**：

| 简化 | 说明 |
|------|------|
| 无 Leader 选举 | 多实例没有自动故障切换 |
| 障碍物随机生成 | 真实场景可能需要加载预设地图 |
| SET_CONFIG 不重建地图 | 参数变更需要 RESET |
| 无访问频率限制 | 没有反爬/限流机制 |
| Redis KEYS pattern | 生产环境应改用 SCAN |
| taskQueue 无持久化保证 | BLPOP 后的任务如果崩溃可能丢失 |
| 无认证鉴权在 Controller 层 | 依赖 Display/Auth 模块 |
